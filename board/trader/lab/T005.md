# Run one strategy over N alternative histories as a background job

## Outcome

One request runs a strategy over N paths of a chosen market type without freezing the server, and returns per-path growth of 1 dollar plus a summary: median, worst, best and how many paths beat each benchmark. The result is saved and can be reopened.

## Why

Boss, 2026-11-12: synthetic market test data "like in the video", whose central chart is a fan of many alternative histories with the median stated in words. Review finding F5: a run blocks the whole server while it computes. The fan chart (T007) needs this job's output.

## Context

Facts at `repos/etoro_trader` (HEAD `846b5cb`; T002 lands before this ticket, T003 and T004 normally too):

- `web/server.py` `create_replay` is declared `async def` and calls `run_replay(...)` directly, so the event loop is blocked for the whole run and every other request waits.
- `simulator_run/replay_runner.py`: `ReplayConfig(strategy, data_source, start, end, seed=42, strategy_params=None, synthetic_overrides=None, include_diagnostics=True)`; `run_replay(cfg)` returns a full tape. The tape's `frames[i]["account"]["equity"]` starts from 10000.0; `benchmarks[SYMBOL]` is a list of dollars of a 10000 start, one per frame, for `SPY, SCHG, SSO, UPRO`; `mandate` has `cagr`, `sso_cagr`, `g1_return`, `g2_risk_score`, `g3_anti_gaming`; `frames[i]["date"]`; `frames[i]["orders"]`.
- Measured in the review prototype: 12 synchronous paths of 3 years took about 110 s, about 9 s a path. A full tape is about 4 MB per replayed year.
- Whether `run_replay` is safe to run twice at the same time in one process is **not known** (it creates stores and a broker per run).
- After T002: `_safe_child`, `_replay_dir()`, `REPORTS_DIR` read at call time, sidecar summaries for replays.
- After T004: `data_source="bootstrap"` with `synthetic_overrides={"mean_block": 21|126|756}`. If T004 has not landed when this ticket is built, `"bootstrap"` simply fails in `load_prices` and the job reports that; the job code does not depend on T004.
- The reference video shows 10,000 histories. At about 9 s a path that is 25 hours here; this ticket caps a job at 500 paths and says so.

## Requirements

1. Starting a job returns at once with a job id; progress and the result are fetched separately.
2. While a job or a single replay runs, other requests are answered.
3. Only one path computes at a time in the process, whether it comes from a job or from a single replay.
4. One job at a time; a second start is refused while one runs.
5. A job never stores tapes: per path it keeps a thinned equity curve and a few numbers.
6. A failing path fails the whole job, naming the seed; no partial result is presented as complete.
7. A running job can be cancelled.
8. Results are reproducible: same request, same result.
9. `real` and `snowflake` are refused as job markets: there is only one real history.

## Design

**`simulator_run/paths_runner.py`** (no web imports; unit-testable)

```python
MAX_PATHS = 500
MAX_POINTS = 260            # points kept per path curve
JOB_MARKETS = ("bootstrap", "synthetic")

@dataclass
class PathsRequest:
    strategy: str
    data_source: str
    start: str
    end: str
    seed: int = 0            # first seed; path k uses seed + k
    n_paths: int = 50
    params: Dict[str, Any] | None = None           # strategy params
    market_params: Dict[str, Any] | None = None    # e.g. {"mean_block": 126}

def validate(req) -> None                 # raises ValueError with one plain sentence
def thin_indexes(n: int, max_points: int = MAX_POINTS) -> List[int]   # evenly spaced, always includes 0 and n-1
def path_row(tape, seed, keep) -> dict    # see below
def summarise(rows) -> dict
def run_paths(req, replay=run_replay, on_progress=None, should_stop=None) -> dict
```

`path_row` reads one tape and returns:

```python
{"seed": seed,
 "equity": [frames[i].account.equity / 10000 for i in keep],          # growth of $1, rounded to 5 decimals
 "final": equity at the last frame / 10000,
 "max_drawdown": most negative of equity / running max - 1 over ALL frames,
 "orders": total orders,
 "cagr": mandate.cagr, "sso_cagr": mandate.sso_cagr,
 "gates_g1_g3": bool(g1 and g2 and g3),
 "bench_final": {sym: benchmarks[sym][-1] / 10000 for sym in ("SPY","SCHG","SSO","UPRO")}}
```

Non-finite numbers become `None`.

`run_paths`: validates; for `k in range(n_paths)`: if `should_stop()` return a result with `status="cancelled"`; build `ReplayConfig(strategy, data_source, start, end, seed=req.seed + k, strategy_params=req.params, synthetic_overrides=req.market_params, include_diagnostics=False)`; call `replay(cfg)`; on the first path compute `keep = thin_indexes(len(frames))` and `dates = [frames[i].date for i in keep]`; later paths must have the same frame count, else raise `ValueError` naming the seed; append `path_row`; drop the tape; call `on_progress(k + 1, n_paths)`. Any exception from path `k` is re-raised as `PathFailed(seed, type name, first line of message capped at 200 characters)`.

Result:

```python
{"status": "done", "request": {...as given...}, "dates": [...], "paths": [rows],
 "summary": {"n": N, "median": ..., "p05": ..., "p25": ..., "p75": ..., "p95": ..., "worst": ..., "best": ...,
             "worst_seed": ..., "best_seed": ..., "median_max_drawdown": ...,
             "beat": {"SPY": count, "SCHG": count, "SSO": count, "UPRO": count},   # path final > that path's benchmark final
             "gates_g1_g3_pass": count, "seconds_per_path": mean},
 "elapsed_s": ...}
```

Percentiles over `final` with `numpy.percentile` (linear). Paths whose `final` is `None` are excluded from percentiles and counted in `summary["invalid"]`.

**`web/server.py`**

- `_replay_lock = threading.Lock()`: held around every `run_replay` call, in `create_replay` and inside the job (pass `replay=lambda cfg: _locked_replay(cfg)`).
- `create_replay`: change `async def` to `def`, so FastAPI runs it in its worker thread pool and the event loop stays free. Body otherwise unchanged apart from the lock.
- Job state: one module-level `_job: Dict[str, Any] | None` guarded by `_job_lock`; fields `job_id`, `status` (`running`, `done`, `failed`, `cancelled`), `done`, `total`, `started_utc`, `error`, `stop` (a `threading.Event`).
- Job id: `"paths_" + UTC "%Y%m%dT%H%M%S" + "_" + 6 hex`; pattern `_PATHS_ID = re.compile(r"paths_[0-9]{8}T[0-9]{6}_[0-9a-f]{6}")`.
- Storage: `REPORTS_DIR / "paths" / f"{job_id}.json"` (result) written once when the job ends as `done`; helper `_paths_dir()` like `_replay_dir()`. `failed` and `cancelled` jobs write nothing.
- Routes:
  - `POST /api/paths` body `{strategy, data_source, start, end, seed=0, n_paths=50, params={}, market_params={}}`. `validate` failure: 400 with its sentence. A job already running: 409 `"a paths job is already running"`. Otherwise start a daemon `threading.Thread` and return 202 `{"job_id": ...}`.
  - `GET /api/paths/{job_id}`: if it is the in-memory job: `{job_id, status, done, total, elapsed_s, error}` and, when `done`, also `result`. Else if the file exists: `{job_id, status: "done", result}`. Else 404. Id checked with `_safe_child(_paths_dir(), job_id, _PATHS_ID, "paths job", ".json")`.
  - `GET /api/paths`: saved results, newest first, without opening the big arrays: each row `{job_id, bytes}` plus the `request` and `summary` read from a small sidecar `{job_id}.meta.json` written with the result. Same missing-sidecar rule as T002.
  - `DELETE /api/paths/{job_id}`: running job with that id: set `stop`, return `{"cancelling": id}`. Saved file: delete it and its sidecar, return `{"deleted": id}`. Else 404.
- A server restart loses a running job; saved results stay. Nothing is deleted at startup.

`validate` rules: `n_paths` integer 1..`MAX_PATHS`; `data_source` in `JOB_MARKETS` (message for `real`: "Many-paths runs need the bootstrap or synthetic market; real history has only one path."); `start < end` as ISO dates; `strategy` non-empty; `seed` integer >= 0.

**Speed.** Sequential, one thread. Expected about 9 s a path: 50 paths about 8 minutes, 500 about 75 minutes. Parallel worker processes would cut that by the number of cores but need each path to run in a separate process on Windows; that is a follow-up ticket once the per-path time is measured here, not part of this one.

**Size.** 500 paths x 260 points x about 8 characters is about 1 MB of curves. The 5 MB limit in Acceptance holds with room.

Why this shape: the job logic is a plain function that takes the replay function as an argument, so it is tested with a fake replay in milliseconds, and the server part is only state and routes.

## Ripple effects

- `create_replay` becomes a thread-pool endpoint → two replay requests can now be accepted at once → `_replay_lock` makes the second wait instead of running concurrently; its request simply takes longer. Tested.
- A single replay requested while a job runs waits for the current path to finish (up to about 10 s), then runs between paths → the job slows by that one replay. Accepted; say so in the report.
- New folder `reports/paths/` → confirm ignored by git (read-only `git check-ignore -v reports/paths/x.json`); report the result; do not edit `.gitignore`.
- T002's replay list and summaries are untouched: the job never writes into `reports/replays/`.
- The summary's `gates_g1_g3_pass` is the number the mandate's G5 needs → T009 may read it; nothing reads it yet.
- Daemon thread → stopping the server abandons a running job without a saved result. Intended.

## Watch

- Tests never run a real replay for job logic: inject a fake `replay` returning a minimal tape built in the test (frames with `date`, `account.equity`, `orders`; `benchmarks`; `mandate`). In `test_web_paths_job.py` monkeypatch `web.server.run_replay`.
- Tests patch `web.server.REPORTS_DIR` to `tmp_path` before creating a `TestClient`.
- Job tests must not sleep-poll for long: make the fake replay block on a `threading.Event` the test controls, to observe `running`, cancellation and the 409 deterministically.
- `max_drawdown` uses all frames, not the thinned ones.
- The first and last kept points must be frame 0 and the last frame, so the fan starts at 1.00 and ends at `final`.
- Do not hold `_job_lock` while a path computes.
- Never put exception text beyond the first line into a response; 200-character cap.
- JSON with `allow_nan=False` after replacing non-finite values.
- No git state changes. No installs. Never read credentials.

## Acceptance

1. `POST /api/paths` returns 202 with a job id while the (blocked) fake replay has not finished; `GET /api/paths/{id}` shows `running` with `done` and `total`.
2. While a job is blocked mid-path, `GET /api/health` answers; measured on the real run in Plan step 4, the worst latency is under 1 second.
3. `n_paths` 0 and 501, an unknown market, `real`, `start >= end`: 400 with one sentence each.
4. A second `POST` while one runs: 409.
5. Finished job: `result.paths` has N rows each with at most 260 points, first point 1.0; `summary` matches hand-computed values for a small fake set (median, worst, best, beat counts, gate count).
6. Same request twice with a deterministic fake replay: identical `result` apart from timing fields.
7. A path that raises: job `failed`, `error` names the seed, no result file written, `GET` returns no `result`.
8. `DELETE` on a running job: status becomes `cancelled`, no file. `DELETE` on a saved job: file and sidecar gone, second call 404.
9. Saved result reopens after a new `TestClient` on the same folder; `GET /api/paths` lists it with `request` and `summary` without parsing the result file (replace the result file with invalid JSON: the list still succeeds).
10. Malformed job ids (`..%5Cx`, `paths_20260101T000000_ABCDEF`) return 400.
11. 100 fake paths of 780 frames: the saved result file is under 5 MB.
12. Two overlapping `POST /api/replay` calls never run `run_replay` concurrently (fake replay records overlap).
13. Existing suites pass: `test_web_replay_store.py`, `test_web_server_paths.py`, `test_web_replay_v05.py`, `scripts/ci_import_check.py`.
14. Builder report: measured seconds per path and worst `/api/health` latency from Plan step 4, and the `git check-ignore` result.
