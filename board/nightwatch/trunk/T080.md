# Unattended demo seed: the armed-session alarm buys and adopts SCHG once, then the session runs

## Outcome

With a one-shot flag set on the phone, the next armed-demo alarm opens the SCHG seed positions, adopts them and then runs the session, with no tap by anyone.

## Why

Boss, 2026-11-13: the PM works only while the US market is closed, and the Boss will not tap anything after the open. Buying SCHG and adopting it both need an open market, and both are operator-only today (T079, T068). The daily alarm already fires at 20:05 UTC while the market is open, so the seed rides on it. Demo account only. This deliberately relaxes two operator confirmations for demo, on the Boss's instruction; it does not touch the real path.

## Requirements

1. The seed runs only from the alarm wake, only when all of these hold: not halted, power allowed, `files/nightwatch_demo/ARM_DEMO` exists, `files/nightwatch_demo/SEED_DEMO` exists.
2. The flag's content is two integers separated by whitespace: count and USD each (for example `5 11000`). Anything else refuses without a network call.
3. One shot: the flag is renamed to `SEED_DEMO.running` before the first network call. A crash at any later point leaves no `SEED_DEMO`, so the seed can never run twice from one flag.
4. All demo checks stay where they are: the seed calls the existing runners and adds no order-placing code of its own.
5. No order is ever resent. Adoption is planned and applied at most 3 times in total.
6. Adoption is attempted only if at least one order was accepted in this run.
7. The seed stops by a hard budget of 10 minutes from its start, so the session still starts inside its window. On budget expiry it stops whatever step it is in between calls and records it.
8. The session runs after the seed whatever the seed's result, exactly as today.
9. The result is persisted on the phone: `files/nightwatch_demo/SEED_DEMO.done` (JSON) and an event-log line. `SEED_DEMO.running` is removed when `.done` is written.
10. No Telegram, FCM, command, intent-extra, boot or UI path can start the seed.

## Design

**Python: `probe/demo_seed.py`**

```python
def run(home: str) -> str:
    """One-shot unattended demo seed. Returns JSON; never raises."""
```

Steps, each appended to a `steps` list as `{"step": name, "status": ..., "detail": redacted text}`:

1. `home` must resolve to a folder named `nightwatch_demo`; else status `refused`.
2. Read `home/SEED_DEMO` (text, ASCII, at most 32 bytes). Parse exactly two base-10 integers. Validate with the same limits as the buy runner (count 1 to 10, USD each 50 to 15000). Invalid: status `refused`, flag renamed to `SEED_DEMO.done` holding the refusal JSON, no network call.
3. Rename `SEED_DEMO` to `SEED_DEMO.running` (`Path.replace`). If the rename fails, status `refused`, stop.
4. `text = demo_manual_buy.run(home, count, usd_each)`. `accepted = number of lines matching "^Order \d+/\d+: accepted"`. `buy_complete = any line starts with "Demo buy complete"`.
5. If `accepted == 0`: status `buy_refused_or_failed`, skip adoption, go to 8.
6. Wait for positions: build a read-role client the same way `adopt_apply` does (`EtoroClient(config.etoro, role="read", repo=None)`), read the SCHG instrument id with `resolve_instrument_id("SCHG")`, and poll `get_portfolio_strict()` every 10 seconds until the count of SCHG positions is at least `baseline + accepted`, or 180 seconds pass. `baseline` is the SCHG position count read once **before** step 4 with the same client code. If the baseline read fails, do not buy: status `refused` (portfolio unreadable), go to 8. A wait timeout is recorded (`positions_visible: false`) and the flow continues to step 7 with what is visible.
7. Adopt: up to 3 attempts of `plan(home)` then, if `planned`, `apply(home, plan_id)`. Stop at the first `applied`. Wait 10 seconds between attempts. Any `refused` or `error` report is recorded per attempt. After 3 attempts without `applied`: status `adoption_not_applied`.
8. Write `SEED_DEMO.done` (JSON: `status`, `count`, `usd_each`, `accepted`, `buy_complete`, `positions_visible`, `adoption_attempts`, `started_utc`, `finished_utc`, `steps`), remove `SEED_DEMO.running`, print one summary line, return the JSON.

Final `status` values: `seeded` (buy complete, all positions visible, adoption applied), `seeded_partial` (adoption applied but fewer orders accepted than asked, or positions not all visible), `adoption_not_applied`, `buy_refused_or_failed`, `refused`, `error`, `budget_exceeded`.

Budget: record `time.monotonic()` at start; before each of steps 4, 6-poll, 7-attempt check `elapsed < 600`; if not, status `budget_exceeded`, go to 8. Step 4 itself is not interrupted once started.

All text that came from a runner is already redacted by that runner; text the seed creates must contain no exception message, only `type(exc).__name__` and the step name (same rule as `demo_manual_buy.py:74-77`). Wrap the whole body so any exception becomes status `error` and step 8 still runs (best effort).

The clock and sleep are injectable (`_sleep`, `_monotonic` module-level names) so tests run instantly.

**Kotlin: `PyBridge.kt`**

```kotlin
/** Alarm-only unattended demo seed (T080). Blocks behind a running session or adoption. */
fun runDemoSeed(context: Context, home: String): String {
    ensureStarted(context)
    return sessionLock.withLock {
        bridgeLock.withLock {
            Python.getInstance().getModule("probe.demo_seed")
                .callAttr("run", home).toString()
        }
    }
}
```

It calls the Python runners directly inside Python, so `runDemoManualBuy`'s `tryLock` path is not used and cannot deadlock.

**Kotlin: `WakeService.kt`**

In step 5b, inside the branch that is about to call `runSessionDry()` (after the halt and busy checks, with `sessionRunning` already set), call `runDemoSeedIfFlagged()` first:

```kotlin
private fun runDemoSeedIfFlagged() {
    val home = File(filesDir, "nightwatch_demo")
    if (!shouldRunDemoSeed(home, HaltFlag.isHalted(this),
            PowerStatus.shouldRunSession(PowerStatus.isCharging(this), PowerStatus.batteryPercent(this)))) return
    val lock = newWakeLock("NightwatchProbe:DemoSeed")
    try {
        lock.acquire(15 * 60 * 1000L)
        store.log("DEMO_SEED_START", "flag present")
        val raw = PyBridge.runDemoSeed(this, home.absolutePath)
        val status = try { JSONObject(raw).optString("status", "unparsed") } catch (_: Exception) { "unparsed" }
        store.log("DEMO_SEED_RESULT", "status=$status")
        NotificationHelper.post(this, "Nightwatch DEMO seed", "status=$status")
    } catch (e: Exception) {
        store.log("DEMO_SEED_FAILED", "error=${e.javaClass.simpleName}")
    } finally {
        if (lock.isHeld) lock.release()
    }
}
```

and in the companion object, pure and unit-testable:

```kotlin
internal fun shouldRunDemoSeed(demoHome: File, halted: Boolean, powerAllowed: Boolean): Boolean =
    !halted && powerAllowed && File(demoHome, "ARM_DEMO").exists() && File(demoHome, "SEED_DEMO").exists()
```

Only the status goes to the event log and notification, never the raw text. A seed failure must not prevent `runSessionDry()`: the call is in its own try/catch and the session call follows unconditionally.

**Change: two phases, driven by two flag files in the demo home.**

- Phase buy (flag `SEED_DEMO`, content `count usd_each`): exactly as designed above through the position wait and the adoption attempts (up to 3). If adoption is applied: final status as above. If at least one order was accepted and adoption was **not** applied: create `SEED_DEMO.adopt` containing `0`, and final status `bought_adoption_pending` (this replaces `adoption_not_applied` for the buy phase).
- Phase adopt (no `SEED_DEMO`... see precedence; flag `SEED_DEMO.adopt`, content one integer `n` = alarms already used, 0 to 5): if the content is not such an integer, or `n >= 5`: rename the flag to `SEED_DEMO.adopt.failed`, status `adoption_abandoned`, no network call. Applied: delete `SEED_DEMO.adopt`, status `adopted`. Not applied: flag stays, status `adoption_pending`. No buy runner call and no write-role client in this phase, ever.
- Precedence: if `SEED_DEMO.adopt` exists, run phase adopt and leave any `SEED_DEMO` untouched. Only when there is no `SEED_DEMO.adopt` does `SEED_DEMO` start phase buy. Neither flag: refused as before.

## Ripple effects

- The seed holds `sessionLock` for up to 10 minutes before the session → the session starts up to 10 minutes after the alarm (20:15 UTC at worst) → still inside the entry window, which closes 25 minutes before the close (20:35 UTC). The 10-minute budget is the control; state the worst-case arithmetic in the report.
- The outer wake lock in `runWakeWork` is 10 minutes and is not reference counted → the seed and the session each take their own lock, as the session already does.
- Positions bought but not adopted (adoption refused three times) → the session that follows meets unannotated SCHG positions → what gate 11 and reconcile do with them is **not known to the PM**. Builder: read the gate and reconcile code for unannotated managed-symbol positions and report the behaviour (refuse, halt or ignore) with file and line. Do not change it.
- The buttons stay → an operator can still buy and adopt by hand. A seed flag and a manual run cannot overlap: both take the same locks.
- T079's acceptance sentence "never from session, alarm or command" is narrowed by this ticket to "never from command, Telegram, FCM, intent or boot; from the alarm only through the one-shot seed". The PM records that on T079.
