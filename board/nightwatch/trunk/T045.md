# T045 — The phone wakes for the dry-run session only on NYSE trading days at close−55 min ET, stops on HALT, and skips on low power

## Outcome
Three known T040 gaps close, still **dry run only, never armed**:
1. **Market-aware alarm.** A new alarm mode `market` fires at the next NYSE trading day's close − 55 min ET (inside the entry window [close−60, close−25]). DST and early closes are handled by the Python calendar on the device. The mode is rescheduled after every wake and on boot.
2. **HALT link.** When the session envelope reports HALT, the app stops scheduling sessions, keeps a persistent (ongoing) notification until resumed, and the Kotlin flag and the Python `HALT` file stay in step. `resume` clears both and reschedules.
3. **Power gating.** Before the session step, the app skips the session when the battery is low and the phone is not charging, logs it, and sends a failure notification. The defaults are below.

## Why
T040 shipped the dry-run session on the phone with three gaps stated in its A2/A5/A7 amendments (`T040.md:122,128,132`) and in `android_entry.py:3-6`:
- the alarm is a device-local fixed `HH:mm` on weekdays, not market or DST aware;
- Kotlin's `HaltFlag` (SharedPreferences) is disconnected from the Python `HALT` file;
- `DesktopHost` reports power gates as satisfied.

These must close before any device-side arming ticket can be considered.

## Design

**D1 — next wake (Python).**
- `next_session_wake_epoch_ms(now_epoch_ms=None)`: take `now` (UTC from the argument, or the real clock), call `next_close_minus(55, after=now)`, and return its UTC epoch milliseconds as an int.
- Fifty-five minutes keeps the fire 5 min inside the entry window's lower bound (close−60) and leaves 30 min before close−25.
- Pure function: no host, DB, network or config reads.
- Errors propagate. The Kotlin caller catches them.

**D2 — envelope `halt` field (Python).**
- After the existing envelope is built, in every path including errors, set `envelope["halt"] = <root>/HALT exists`.
- Compute it from `Path(base_dir) / "HALT"`, so it works even if `DesktopHost` construction failed. Wrap it in try/except, falling back to `False` only if the existence check itself raises.
- The `out_of_window` path reports it too. Existing fields are unchanged.

**D3 — `market` alarm mode (Kotlin).**
- `AlarmScheduler.scheduleMarket(context): Long?` sets `KEY_MODE="market"`. It gets the trigger from `PyBridge.nextSessionWakeEpochMs(context)`, which calls D1 with no argument, then calls `schedule(context, t)`.
- On a Python exception it logs `ALARM_MARKET_COMPUTE_FAILED`, posts a failure notification, and returns `null`. It never falls back to a fixed time.
- `rescheduleFromSavedState` adds `"market" -> scheduleMarket(context)`.
- `currentNextFireEpochMs` for market mode returns the saved last-scheduled epoch. Store `KEY_MARKET_NEXT` in `schedule()` when the mode is market, so the UI does not call Python on the main thread.
- **HALT precedence:** `scheduleMarket` returns `null` and logs `ALARM_SUPPRESSED_HALT` when `HaltFlag.isHalted`. This also covers boot.

**D4 — HALT link (Kotlin), single source: the Python file `filesDir/nightwatch_config/HALT`.**
- After `runSessionDry` parses the envelope:
  - If `halt == true` (or `status == "preflight_failed" && failed_gate == 1`): set `HaltFlag` true, cancel the alarm (`AlarmScheduler.cancel`), post the ongoing HALT notification ("Nightwatch HALTED: sessions stopped until resume"), and log `HALT_LINKED`.
  - If `halt == false` and `HaltFlag` is true (operator removed the file by other means): leave it alone. Only `resume` clears it.
- Because the early reschedule at `WakeService.kt:70-77` runs before the session, D3's HALT precedence means a halted app does not reschedule. The alarm armed earlier in this wake is cancelled by D4.
- `CommandHandler`:
  - `halt` also creates the HALT file (content "kotlin halt command <ISO time>").
  - `resume` deletes it, clears `HaltFlag`, clears the ongoing notification, and calls `rescheduleFromSavedState`.
  - Both log what they did. File errors are logged and notified, and the flag change still happens.
  - `resume` remains an operator, HMAC-verified command (unchanged verification).

**D5 — power gate (Kotlin), in `WakeService` immediately before the session step.**
- Defaults (constants in `WakeService`, not secrets or config): **run if charging, or if battery ≥ 30 %; otherwise skip.**
  - A dry run needs only a few minutes of radio and CPU.
  - 30 % keeps a margin for an overnight standby.
  - Charging always allows the run.
- On skip:
  - log `SESSION_SKIPPED_POWER battery=<pct> charging=<bool>`;
  - post a failure notification;
  - do not call Python;
  - still finalize normally (the reschedule already happened early).
- `PowerStatus.batteryPercent` returning −1 (unknown) counts as low unless charging.

**D6 — wake-lock and finalization.** Unchanged. All new steps are wrapped so exceptions are logged and finalization and `stopSelf` still run, as T040 A5 requires.

## Amendments after precheck (2026-10-30, PM accepts all eight ranked corrections and the recommended options; latest wins)

**Split:** this ticket is now **T045 = Python helper + HALT latch + scheduling** (D1-D4, D6, A1-A3, A6-A7, B1-B5 below). **Power gating (D5, A4-A5) and the JVM test source set (A8) move to T046**, which depends on T045. Acceptance 5's Kotlin checklist for power moves with them.

**A1 — HALT policy "file + resume-only latch".**
- `HaltFlag` is a latch that is checked **before every session call, whatever the alarm mode** (nightly, minutes, absolute or market). If it is latched: log `SESSION_SKIPPED_HALT`, make no Python session call, and still finalize.
- The `halt` command itself cancels the alarm and posts the ongoing HALT notification. It does not wait for a session.
- On boot, reconcile the HALT file into the latch **before** rescheduling: if the file exists, latch, then reschedule (which is then suppressed).
- Only a **successful** `resume` clears the latch. A missing file never clears it.

**A2 — fail-closed resume and halt.**
- `resume` clears the latch, clears the notification and reschedules only after confirming the HALT file is absent: delete it, then check that it no longer exists.
- If the delete or the check fails, the latch stays set and a failure notification is posted.
- `halt`: if creating the file fails, the latch is still set, plus a failure notification.

**A3 — truthful scheduling.**
- `schedule()` returns success or failure. It returns `null`/false when exact-alarm permission is denied or `setAlarmClock` throws `SecurityException`.
- Persist `KEY_MARKET_NEXT` only on success, and clear it on cancel or failure.
- When switching modes (to market, or from market to anything else), cancel the old alarm first, even if the new market scheduling then fails.
- `scheduleMarket` returns `null` on any failure. Callers and the UI show "not scheduled", never a stale time.

**A6 — split no-broker acceptance (replaces Acceptance 3).**
- (a) `next_session_wake_epoch_ms`: a test proves no host, DB, config or network access. Patch these to raise, and the function still returns.
- (b) Session route: existing read calls stay. The session is never armed and makes no broker write; prove it with the T040 A1 write trap with the `halt` field present.

**A7 — envelope tests.**
- Update the existing envelope assertions in `tests/test_android_entry.py` to include `halt`.
- Add halt-present and halt-absent assertions on every path: `refused`, `out_of_window`, `busy`, `already_ran`/`previous_unfinished`, engine statuses, `error`, and the serialization-error fallback, whose literal JSON must also carry `"halt"`.

**B1 — threading.** No Python call on the UI thread or inside a `BroadcastReceiver.onReceive` body.
- `scheduleMarket` runs on a background dispatcher. `MainActivity` uses a coroutine and shows the result.
- Receivers use `goAsync()` with a bounded worker; see B2.

**B2 — bounded async boot strategy.**
- On targetSdk 36, do not rely on starting the dataSync foreground service from `BOOT_COMPLETED`.
- `BootReceiver` uses `goAsync()` plus a coroutine with a hard timeout under 10 s. Within that budget it reconciles HALT (A1) and computes and schedules the market alarm.
- On timeout: log `BOOT_RESCHEDULE_TIMEOUT` and post a failure notification. The next app open or command repairs it.
- The existing `WakeService` boot trigger is kept only if it already works. If it is kept, say so in the report. The schedule must not depend on it.

**B3 — stable HALT notification.** One fixed notification ID for the ongoing HALT notification.
- It is re-posted on boot and on every wake while latched.
- Successful `resume` cancels it.

**B4 — DST tests (replaces the DST line in Acceptance 1).**
- Trading day 2026-10-30 (EDT): wake 15:05 ET = **19:05 UTC**.
- Trading day 2026-11-02 (EST, after the 2026-11-01 change): wake **20:05 UTC**.
- Same check across the March change: 2026-03-06 EST gives 20:05 UTC; 2026-03-09 EDT gives 19:05 UTC.

**B5 — timing caveat.** `setAlarmClock` fires at the scheduled instant, but the session's T−30 wait and the network can shift it. The entry window [close−60, close−25] stays the guard. State in the README or code comment that the 55-minute lead is a margin, not a guarantee. Device timing is unverified until the Z10 proof.
