# T020 — `Repo.insert_snapshot` writes the snapshot and all its positions, or nothing

## Outcome
A failure partway through `insert_snapshot` leaves **zero** rows of that snapshot in `portfolio_snapshots` and `portfolio_snapshot_positions`, even when a later write on the same connection commits (e.g. `finish_session`). T010 can then trust that every snapshot row is whole.

## Why
- T017 leftover. T010's loss comparison reads consecutive snapshots, and a half-written one would corrupt it.
- Consultant verify item: "injected failure during position insertion leaves zero partial snapshots".

## Context (jack 2026-10-09, read; P = `app/src/main/python/nightwatch`)
- `P/db/repo.py:63–79` `connect(path)` uses `isolation_level="DEFERRED"`, not autocommit.
- `P/db/repo.py:1843–1876` `insert_snapshot(self, snapshot) -> int`: it inserts the header row, loops over the position rows, then calls `self.conn.commit()` once. There is **no try/rollback**. A mid-loop exception leaves the earlier inserts pending in the open transaction.
- `P/engine/session.py:401–416` (inside `_run_session_core`, since T018): catches the snapshot exception and then calls `repo.finish_session(...)`, whose `update_session` commits (`repo.py:841–867`). **The partial snapshot is committed by that later write.**
- The existing pattern is `insert_lot_annotations` (`repo.py:1415–1488`): try, `rollback()` on error, `commit()` on success.
- Tests:
  - `tests/test_repo.py::test_portfolio_snapshot_round_trip_with_positions` (628–657) covers success only;
  - `tests/test_session_snapshot.py::test_session_snapshot_report_not_gate` (123–160) raises before any insert.

## Scope
- `P/db/repo.py` `insert_snapshot` only.
- New tests in `tests/test_repo.py`.

## Out of scope
- `upsert_bars` (its docstring says "one transaction" but it commits per row; jack noted this, so record it, do not fix).
- A general transaction helper.
- session.py.

## Design
Follow the `insert_lot_annotations` pattern exactly:
```python
try:
    <header insert>; <position inserts>
except BaseException:
    self.conn.rollback()
    raise
self.conn.commit()
return snapshot_id
```
- `BaseException`, so a KeyboardInterrupt mid-insert also rolls back. Re-raise unchanged.
- Rollback also drops any unrelated uncommitted writes pending on the connection. Accepted: the repo commits after each write method (the jack inventory shows no caller that relies on an open transaction across calls). Precheck confirmed: the session path`s prior `insert_decision` commits (`repo.py:940`), so nothing is pending.

## Plan
1. `repo.py`: wrap as in the Design. No other edits.
2. `tests/test_repo.py`:
   - `test_insert_snapshot_mid_failure_leaves_no_rows`: make a snapshot with 3 positions, where the 3rd has a value that makes its insert raise. Force it with a duplicate: positions ids "1", "2", "1". `schema.sql:325` has `UNIQUE (snapshot_id, position_id)`, so the 3rd insert raises `sqlite3.IntegrityError`. Then `insert_snapshot` raises; then `repo.finish_session(...)` (a later commit) runs on a real session row; then both tables have 0 rows for that snapshot.
   - The success round trip is still green.
3. Prove.

## Ripple effects
- `insert_snapshot` callers: session.py:411 is the only application caller (plus the direct test caller `tests/test_repo.py:635`) → behaviour on success is unchanged. On failure, the rows are now absent instead of partial, and session.py already reports `snapshot failed`.
- Shared connection rollback → it could drop another pending write. Precheck checks the callers.

- Do not add commits inside the loop.
