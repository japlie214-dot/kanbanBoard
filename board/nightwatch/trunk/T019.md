# T019 — The boss sends `/resume <reason>` from their Telegram chat. The next session applies it before gate 1, and the reason is saved.

## Outcome
- At the start of every `run_session` (before preflight), the app fetches pending Telegram updates once and runs every command from the boss's chat in order, then acknowledges them. Delivery is at-least-once: a crash before the acknowledgement re-runs the commands next time, and `/halt`/`/resume` tolerate that.
- `/resume <reason>`: clears HALT only if a reason is given **and** the message was sent after the HALT was set. It replies `HALT cleared (reason: ...)`.
- A bare `/resume` replies with usage and changes nothing.
- `/halt [reason]` sets HALT with the reason (source `telegram`).
- Every command is stored in the `commands` table, with its full text.
- Messages from any other chat are ignored and logged, never answered (unchanged).
- The CLI `nightwatch poll` does the same on demand.

## Why
- Boss 2026-10-07: HALT is cleared only by the boss, via Telegram `/resume <reason>`. The PM never clears it.
- Boss 2026-10-10 approved the auth and polling design below.
- Facts (jack 2026-10-09, read-only inventory; copied here):
  - `notify/commands.handle` exists but **nothing calls it at runtime**;
  - Telegram commands require HMAC + counter, which a human typing in Telegram cannot produce;
  - `/resume` ignores trailing text.

## Design (PM decisions)
1. **Auth split** in `handle`:
   - `channel == "telegram"`: the authorization is exactly `chat_id == config.telegram.allowed_chat_id` (as strings). **Skip** the counter/HMAC/secret/replay checks for Telegram only.
   - `channel == "fcm"`: unchanged (HMAC + counter + replay).
   - Rationale in a comment: Telegram guarantees chat identity, and a typed message cannot carry an HMAC (boss 2026-10-10).
2. **Arguments:** `handle` keeps `raw_command` whole. New helper `_args(raw_command) -> str` = the text after the first whitespace-delimited word, stripped. `_dispatch` gains `args: str` and `message_ts: datetime | None` parameters (keyword-only, defaults `""` and None).
3. **`/resume`:**
   - `args == ""` → reply `"Usage: /resume <reason>. HALT unchanged."`, the verdict stays accepted, and the action is none.
   - HALT absent → `"HALT was not set."`.
   - `h = read_halt(host)`. If `h["set_at"]` is not None and `message_ts` is not None and `message_ts <= datetime.fromisoformat(h["set_at"])` (`set_at` is a UTC ISO string with an offset, written by `write_halt`) → reply `"Ignored: this /resume was sent before the current HALT was set ({set_at}). Send /resume again."` and do NOT clear. This guards against a resume written before a new HALT.
   - Else `clear_halt(host)` → reply `f"HALT cleared (reason: {args}). Previous HALT: {h['reason']} (source {h['source']})."`
4. **`/halt [reason]`:** `write_halt(host, reason=args or "halted via Telegram", source="telegram")` → reply as today.
5. **Persistence:** the accepted row's `command` = the full `raw_command` (which already holds the reason). Add `reason=args or None` to the accepted insert for `/resume` and `/halt` only. In `schema.sql`, the HMAC comment (:354–358) becomes "FCM commands carry an HMAC counter; Telegram commands are authorized by chat id only (T019)", and the `commands.reason` column doc becomes "rejection reason, or the operator reason for /halt and /resume". No migration is needed: the column exists.
6. **`P/notify/poll.py`**, one responsibility: pull and apply Telegram commands.
   - `process_pending(notifier: TelegramNotifier, repo: Repo, host: Host, config: Config) -> list[CommandResult]`:
     - `updates = notifier.get_updates()`. If empty → return `[]`.
     - Sort by `update_id`. For each update with `message.text` starting with `/`: `ts = datetime.fromtimestamp(message["date"], timezone.utc)`, `r = handle(repo, host, config, channel="telegram", sender_id=str(message["from"]["id"]) if "from" else "", raw_command=text, chat_id=str(message["chat"]["id"]), message_ts=ts)`. If `r.reply` is set → `notifier.send(r.reply, event="command_reply")`. Exceptions are caught per update and logged; processing continues.
     - Non-command updates are skipped.
     - `results` = the `CommandResult` of every update passed to `handle` (including rejected ones), not the skipped or raising ones.
     - Finally **acknowledge**: `notifier.get_updates(offset=max_update_id + 1)`, where `max_update_id` covers **all** fetched updates, including skipped, rejected and raising ones. A raising update is logged and acknowledged, so a poison message cannot block every session. Ack after processing, so a crash mid-way re-runs the commands next time; `/halt` and `/resume` are idempotent enough.
   - `handle` gains `message_ts: datetime | None = None` and passes it to `_dispatch`.
7. **Session:** in `run_session` (the wrapper), **before** `_run_session_core`: `if notifier is not None:` `try: process_pending(notifier, repo, host, config)` `except Exception: log warning`. A poll failure never blocks the session; gate 1 then reads the flag as usual.
8. **CLI:** `nightwatch poll`: build the notifier like `_cmd_run`, call `process_pending`, and print `f"{len(results)} command(s) processed"`.
9. **DESIGN.md §8.2:** the command table gets `/resume <reason>` (required) and `/halt [reason]`. Auth paragraph: "Telegram: chat-id allowlist only (boss decision 2026-10-10); FCM: HMAC + counter." Inbound: "polled once at each session start, and via `nightwatch poll`."
10. **Why this shape:**
    - The poll is a separate unit (`poll.py`), so session.py only calls it.
    - Command rules stay in `commands.py`.
    - The stale-resume guard uses T022's `set_at`, so it needs no new storage.

## Ripple effects
- **Telegram security model** → anyone controlling the boss's Telegram account can `/halt` or `/resume`. Accepted by the boss 2026-10-10 (two-step verification recommended). FCM is unchanged.
- **Existing HMAC tests on the telegram channel** → they change channel to fcm. Coverage is kept.
- **Every session makes one poll call, one ack call if there were updates, and one reply per command** → negligible. A failure is swallowed.
- **Acknowledging updates deletes them server-side** → `telegram-test`'s pending count will show 0 after sessions. That is expected.
- **The `/resume` behaviour changes:** a bare `/resume` no longer clears. This is intended.
