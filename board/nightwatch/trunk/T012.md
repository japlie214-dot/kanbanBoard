# T012 — Every position the app opens carries no broker take-profit

## Outcome
`EtoroClient.clear_take_profit(request_id, position_id)` sends eToro's documented edit-position call, which removes the take-profit from one position. A later read of the position then shows `isNoTakeProfit: true` or no positive `takeProfitRate`. eToro's automatic +1000% take-profit therefore never sells an app lot behind the app's back. This ticket builds and tests the method offline. A single boss-approved DEMO order proves it live (part 2). The executor calls it after each fill in S7.

## Why
- Operator 2026-10-02: eToro adds its default take-profit to orders the app places. Decision the same day: remove it (project.md §11).
- A take-profit fill closes a lot outside the app. Gate 11 then halts every session until a human reconciles.
- The method can be built and tested now, without market hours. The engine does not place orders yet, so nothing calls it until S7.

## Context (jack inventory 2026-10-08, read; P = `app/src/main/python/nightwatch`)
- `P/etoro/client.py` has 4 POST call sites and **no PUT/PATCH/DELETE**. Writes: `place_buy_order` (1346) and `close_position` (1447). Both take a caller-supplied `request_id`, and `_request` sends it as `x-request-id` via `auth.build_headers` (`client.py:306–312`, `auth.py:51–67`).
- `_request` (`client.py:283–367`): `request_class="write"` gives `attempt_limit = 1`, so writes are never retried. The status mapping is: timeout `EtoroTimeoutError`, network `EtoroNetworkError`, 401/403 `EtoroAuthError`, 429 `EtoroRateLimitError`, 5xx `EtoroServerError`, other 4xx `EtoroValidationError`.
- The demo/real path segment is `self._demo()`, which returns `"demo/"` or `""` (`client.py:383–391`, `config.py:176–181`).
- Rate buckets: write 20/min (`ratelimit.py:32–40`).
- Take-profit is read in `_parse_position` (`client.py:775–783`: `takeProfitRate`, `isNoTakeProfit`). Detection is `engine/preflight.py:1147` `find_broker_take_profits`.
- The fill's position id is `OrderResult.position_id` (`models.py:518–539`), parsed from `positionExecutions` (`client.py:1864–1887`).
- Tests: `tests/test_etoro_client.py`, fake HTTP `ScriptedTransport` (52–70), wrapped by `httpx.MockTransport`, offline.
- The only `place_buy_order` caller is the probe `probes/order_latency.py:248–278`. `engine/executor.py` is a TODO.

## Official docs (PM read in browser 2026-10-02, api-portal.etoro.com)
- `PATCH /api/v2/trading/demo/positions/{positionId}` with body `{"clearTakeProfit": true}` and header `x-request-id`.
- It returns **202**, accepted and asynchronous, with body fields `operationId`, `positionId`, `referenceId`. Docs: "When true, removes take-profit from the position."
- The real-account path is presumably `/api/v2/trading/positions/{positionId}`. **Unconfirmed.**
- v2 create-order has `takeProfitRate` (≥ 0, optional) and **no** `isNoTakeProfit`. The meaning of 0 or omitted is undocumented, so we do not rely on it.

## Design (PM decisions)
1. `@dataclass(frozen=True) class EditPositionAck: operation_id: str | None; position_id: str | None; reference_id: str | None; status_code: int`, in `models.py` next to `OrderResult`.
2. `EtoroClient.clear_take_profit(self, request_id: str, position_id: str) -> EditPositionAck`:
   - `request_id` is required and non-empty, else `ValueError` before any HTTP. This is deliberately stricter than `place_buy_order`, which accepts an empty id (precheck: `auth.py:65–66` then generates a fresh one the caller never persisted). Docstring: the caller persists the id before the call. Leave `place_buy_order` unchanged here; that gap is recorded for S7.
   - `position_id` must be non-empty and all digits (eToro ids are numeric), else `ValueError`. This blocks path injection.
   - **Real mode fails closed:** if `self._demo() == ""`, raise `EtoroValidationError("clear_take_profit: real-account path unconfirmed (T012)")` before any HTTP. Lift this only after the real path is confirmed.
   - Request: method `"PATCH"`, URL `/api/v2/trading/{self._demo()}positions/{position_id}`, JSON body exactly `{"clearTakeProfit": True}`, `request_class="write"`, and `request_id` passed through the same way `place_buy_order` does.
   - `_request` already accepts any `method: str` (precheck: `client.py:283–312`). Do not change `_request`.
   - Response: accept **200 or 202**. Parse the JSON body if it is an object. Read `operationId`, `positionId` and `referenceId` (each `str(...)` if present, else None). A non-object or empty body gives all three None. Return `EditPositionAck(..., status_code=resp.status_code)`.
   - If the body's `positionId` is present and differs from the argument, raise `EtoroValidationError` (wrong-identity guard, same spirit as `lookup_order`).
   - Errors follow the existing `_request` mapping. No retry, because it is a write.
3. No read-back inside the method. 202 is asynchronous, so confirmation is the caller's job: re-read the portfolio and check with `find_broker_take_profits`. The S7 executor owns that step. Why: one responsibility each. The write stays a pure call, and verification reuses existing detection.
