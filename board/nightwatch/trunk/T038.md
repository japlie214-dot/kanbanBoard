# T038 — An armed session closes UPRO lots, persists the confirmed sale effects, rereads cash, then runs the buys; anything SCHG-sell is refused before any order

## Outcome
An armed session (`mode="live"` + `NIGHTWATCH_ARM`):
1. At gate 11, recovers unfinished closes, then unfinished buys.
2. Decides once.
3. Refuses the whole execution if the decision contains anything outside the supported set (SCHG sells, among others).
4. Executes UPRO full closes against a fresh strict portfolio.
5. On full confirmation, saves a sell-only checkpoint: the new sale bucket plus recyclable cash and sale-batch fields.
6. Rereads cash, applies limits and executes the decision's buys (SCHG and UPRO opens).
7. Saves the full new state only when every close was confirmed and every buy filled.
8. Takes the post-execution snapshot.

The dry run is unchanged.

## Design (PM decisions)
1. **One decision per session, phase 'single'.**
   - No phase-B `decide`. Calling `decide` again would either lose the sale's effects (the closed lots are gone, so no bucket and no recyclable proceeds) or double-count them (feeding phase A's `new_state` also carries simulated buy consumption of `recyclable_cash`, `:860-866`).
   - The single `decide` already models the sale and same-day buys together, with `bars` incremented exactly once (§7.1).
   - The "sell → reread → buy" ordering is achieved by executing closes first and sizing buys against fresh cash through the limits.
   - The decision row stays phase 'single'. T034's A/B support is unused by this ticket.
2. **Gate 11 recovery, armed only.**
   - The `recover` callable runs `recover_unfinished_closes(repo=…, client=…)` first, then `recover_unfinished(...)` as in T030. Both reports go to the holder.
   - A raise from either fails gate 11 (the T030 pattern).
   - If the close report has `blocks_buys`: status `halted_before_execution`, reason `"; execution skipped: unresolved close at recovery"`, no closes, no buys, no save. Snapshot as T030 5b.
   - No HALT for close recovery; gate 11 reconciliation already sees the broker state.
   - The buy-recovery TP rule is unchanged.
3. **Supported intents.** Each intent must be one of:
   - a UPRO close with `amount is None` and a non-empty `position_ref`;
   - a SCHG open with amount > 0;
   - a UPRO open with amount > 0 and book `catapult`, or book `reentry` with `bucket_id`.

   Anything else (SCHG close included) → status `armed_refused_intents`, reason `"armed: unsupported intents (SCHG sells unsupported in S7-3b): <summary>"`, no order, no save. The T030 refusal text is replaced.
4. **Closes first.**
   - `closes = [i for i in d.intents if i.side == "close"]`. If non-empty, take a fresh strict read: `positions = client.get_portfolio_strict()`, `positions_by_id = {p.position_id: p for p in positions}`.
   - Call `execute_closes(..., instrument_ids=mi.instrument_ids, positions_by_id=..., deadline=close−5 min, now=host.now)` inside `try/except Exception`.
   - A raise from the strict read → reason `"close snapshot failed: …"`, status `executed_partial`, no buys, no save, no HALT (nothing was sent).
   - A raise from `execute_closes` → reason `"close execution error: …"`, status `executed_partial`, HALT via `halt_for_tp`-style write with text `"close state unknown after executor error"`.
5. **Close outcome handling.**
   - If any result is `unverified`: write HALT `"close not verified for position(s) <ids>"`, using the same try/except and `halt_error` as T030.
   - If `report.blocks_buys`: skip buys, no full save, status `executed_partial`. CLI exits 1 (the existing allowlist excludes it).
   - `orders_sent = True` once any close intent was persisted.
6. **Sell-only checkpoint**, only when closes exist, every result is `confirmed`, `deferred` is empty and `stopped` is None:
   1. **New buckets:** `[b for b in d.updated_buckets if b.bucket_id not in {x.bucket_id for x in inputs.buckets}]`. Upsert each as a `Bucket(... same fields, is_active=True)`; upsert is idempotent by `bucket_id`.
   2. **Checkpoint state:** `replace(loaded_state, recyclable_cash=rc, sale_batch_sequence=d.new_state.sale_batch_sequence, sale_batch_date=d.new_state.sale_batch_date, trail_state=d.new_state.trail_state)`. `bars`, `ath`, `below_streak` and budget fields stay as loaded.
      - If new buckets exist (new-ATH sale): `rc = loaded_state.recyclable_cash`.
      - Otherwise: `rc = _floor_cents(loaded_state.recyclable_cash + _floor_cents(sum(inputs.upro_price * lot.units for lot in inputs.open_lots if lot.position_ref in closed_refs)))`. This is the exact formula of `ladder.py:676-677,857`; import `_floor_cents` from `..strategy.ladder`.
   3. `save(repo, checkpoint)`, before any buy. If buys later fail, this is the state the next session re-decides from (§7.3); `bars` is not advanced.
7. **Buys.**
   - `buys = [i for i in d.intents if i.side == "open"]`.
   - Reread `balance = client.get_balance()` after closes if any close was sent. Fresh sleeve cash = `max(0, balance.available_cash - config.strategy.cash_reserve_usd)`.
   - `apply_submission_limits(buys, cap_usd=…, reserved_usd=repo.reserved_buy_usd(iso), cash_usd=fresh sleeve cash (or inputs.cash when no close was sent), open_lots=len(repo.list_lot_annotations(is_open=True)), max_open_lots=…, min_order_usd=…)`, then `execute_buys(...)` exactly as T030 with `intents=accepted`.
   - `max_orders_per_session` limits **buys only**, as T028 defines it. Closes are not counted, and stop on the first uncertainty anyway.
   - The recovery-TP skip (T030 5b) is checked before closes and skips both closes and buys.
8. **Reentry bucket updates.** These happen right after `execute_buys`, independent of the final save. This is what stops a filled tranche being bought twice. For each `ExecutedBuy` with outcome `filled` and `intent.bucket_id`:
   - if the bucket is in `d.updated_buckets`, upsert that version;
   - otherwise (the ladder dropped it after its 3rd tranche) upsert the input bucket with `tranches_bought + 1, is_active=False`.
9. **Final save.**
   - Only when all closes were confirmed (or there were none) and the T030 buy rule holds (Design 6 of T030, with `len(results) == len(buys)`).
   - Then `save(repo, d.new_state)` (bars +1 once), and upsert every `d.updated_buckets` entry.
   - Input buckets absent from `updated_buckets` and not handled in 8 are upserted with `is_active=False, expired_at=iso`.
   - Otherwise the reason gets `"strategy state not saved: <condition>"`. The checkpoint from 6 stays if it was written.
10. **Snapshot and alerts:** as T030 (phase `post_execution`, balance reread when `orders_sent`, TP HALT and `tp_not_cleared`).
11. **Statuses:**
    - `executed`: closes all confirmed or none, buys attempted per rules;
    - `executed_partial`: any close not confirmed, a snapshot error or an executor error;
    - `halted_before_execution`;
    - `armed_refused_intents`.
12. **Dry run:** unchanged. No close recovery, no closes, no saves.

### A1. Sale effects are durable and applied exactly once (finding 1)
- The Design 6 rule "checkpoint only if every close confirmed" is **dropped**. Sale effects are applied per confirmed close instead.
- Migration `P/db/migrations/010_sale_effects_bucket_fills.sql` creates the table `sale_effects`:
  - `id INTEGER PRIMARY KEY`
  - `intent_id INTEGER NOT NULL UNIQUE REFERENCES intents(id)` — the UPRO close intent
  - `position_id TEXT NOT NULL`
  - `gross_proceeds_cents INTEGER NOT NULL CHECK (gross_proceeds_cents >= 0)`
  - `classification TEXT NOT NULL CHECK (classification IN ('bucket','recyclable'))`
  - `bucket_json TEXT` (nullable)
  - `created_at TEXT NOT NULL`
  - `applied_at TEXT`
- Proceeds are computed per lot with the ladder's formula: `_floor_cents(upro_price * lot.units)`, matching `ladder.py:676-677`. Classification comes from the decision: 'bucket' when it created a `ReentryBucket` (`:848-855`), otherwise 'recyclable' (`:857`).
- A new-ATH batch has several close intents but must create one bucket. Store the bucket payload once: on the batch's first row, or on a per-batch row. The `ReentryBucket` amount is the sum of the batch's confirmed proceeds, or the decision's bucket amount if the whole batch confirms. The builder picks one rule, documents it in the test, and the test proves exactly one bucket.
- The session inserts one `sale_effects` row per close intent **before** `execute_closes`: in the decision transaction, or immediately after it, committed before any send.
  - If that insert fails, nothing is sent. The status is `halted_before_execution` with no HALT.
- New repo method `apply_sale_effect(intent_id) -> bool`, one transaction:
  - It applies only when the intent has a `close_observations` row with `observed_status='confirmed_full_close'` and the row's `applied_at IS NULL`.
  - A 'bucket' row with a payload creates the bucket.
  - A 'recyclable' row adds `gross_proceeds_cents` to the persisted strategy state's `recyclable_cash`: load, add, save, with other fields unchanged.
  - It sets `applied_at` and returns True. Otherwise it returns False. It is idempotent.
- It is called in two places:
  - (a) in the session, right after `execute_closes`, for each confirmed close in the report;
  - (b) in a new **pre-decide reconcile** step, after gate 11's two recoveries and before `build_ladder_inputs`/`decide`. It applies every unapplied `sale_effects` row whose close is confirmed. This covers a confirmed prefix plus an unresolved close, a crash after confirmation, and a confirmation that arrives during next-session recovery.
- The final narrow save (T030 rule) must not overwrite or double-count applied effects.
  - Build the final state's `recyclable_cash` from the **reloaded** persisted value, minus any `recyclable_cash` the filled buys consumed per the decision.
  - Exclude the decision's own sale-proceeds addition and its new sale bucket, since the repo method already applied both.
  - Test: a recyclable sale plus a fully filled same-session buy ends with the exact expected cents. A bucket sale ends with exactly one bucket.
- Tests in the new `tests/test_sale_effects.py` (real SQLite with all migrations):
  - a confirmed prefix plus an unresolved close: A is applied, B is not; B applies in the next reconcile after recovery confirms it;
  - a crash between confirmation and apply: the reconcile applies it once;
  - a repeated reconcile does not double-add;
  - the bucket classification creates exactly one bucket;
  - a rejected close is never applied;
  - a `sale_effects` insert failure means zero close sends.

### A2. Bucket fills are applied exactly once (finding 2)
