# T024 — A write with an empty request id never reaches eToro, and a close order is polled on eToro's close-order route

## Outcome
- `place_buy_order` and `close_position` raise `ValueError` before any HTTP call when `request_id` is empty or whitespace. Today `auth.build_headers` silently swaps in a fresh UUID, which breaks recovery by referenceId.
- `poll_order_to_terminal` can poll a **close** order via `lookup_close_order`. On 2026-10-09 the generic lookup returned 404 for a filled demo close.
- The write-response order-id recovery for closes no longer goes through the generic lookup.

## Why
- The S7 plan, item 1 (boss approved 2026-10-10). The executor depends on these primitives.
- Live evidence: 2026-10-09 demo close `close_position` → `poll_order_to_terminal(order_id=…)` → 404 "Order was not found for OrderID=387742157", although the position was closed (portfolio empty).

## Context (jack 2026-10-10, read; P = `app/src/main/python/nightwatch`)
- `P/etoro/client.py`:
  - `place_buy_order(self, request_id: str, instrument_id: int, amount_usd: float) -> str` (:1347–1374). It has no empty-id validation.
  - `close_position(self, request_id: str, position_id: str, instrument_id: int, units_to_deduct: float | None = None) -> str` (:1448–1501). It has no empty-id validation.
  - `clear_take_profit` already validates (:1510–1511). Copy that style.
- `P/etoro/auth.py:51–66`: `build_headers` uses `request_id or new_request_id()`.
- `lookup_order(*, order_id=None, reference_id=None, response_capture=...) -> OrderResult` (:1548–1609): v2 `/api/v2/trading/info/{demo/}orders:lookup`. On a demo order-id 404 it falls back to v1 `/api/v1/trading/info/demo/orders/{id}`.
- `lookup_close_order(self, order_id: str | int) -> OrderResult` (:1611–1632): `/api/v1/trading/info/{demo/}close-orders/{orderId}`. Tested at `tests/test_etoro_client.py:566–583`. Used by the probe close poll (`probes/order_latency.py:185–201`) and the Android `demo_cleanup.py:76–139`, but **not** by `EtoroClient.poll_order_to_terminal`.
- `poll_order_to_terminal(self, *, order_id=None, reference_id=None, interval_seconds=None, timeout_seconds=None) -> PollResult` (:1992–2030). It always calls `lookup_order`.
- `_order_id_from_write_response` (~:1390–1443): if a write response lacks an order id, it recovers via the generic lookup by `reference_id=request_id`. Both buy and close use it (`what="close_position"`).

## Out of scope

## Design (PM decisions)
1. **Request-id validation:** at the top of `place_buy_order` and `close_position`, `if not request_id or not request_id.strip(): raise ValueError("<method>: request_id must be non-empty (caller persists it first)")`. This happens before any HTTP.
2. **Close polling:** `poll_order_to_terminal` gains the keyword `kind: str = "open"`.
   - `kind == "close"` requires `order_id` (else `ValueError`) and uses `self.lookup_close_order(order_id)` for every poll.
   - `kind == "open"`: unchanged.
   - Any other kind → `ValueError`.
   - Polling cadence, timeout and `PollResult` are unchanged.
3. **Close write-response recovery:** in `_order_id_from_write_response`, when `what == "close_position"` and the response lacks an order id, **raise** `EtoroValidationError("close_position: response had no order id; close recovery by reference is unverified (T024) -- reconcile from portfolio, do not resubmit")`. Do not call the generic lookup. The buy path is unchanged.
4. **Why:** fail closed. An unverified recovery route must never be guessed. The executor (S7-3) reconciles closes from the portfolio.

## Plan
1. Implement Design 1–3.
2. Tests (`ScriptedTransport`, offline):
   - an empty or whitespace request_id for buy and for close → ValueError, and the transport saw **0** requests (4 cases);

4. Prove.
