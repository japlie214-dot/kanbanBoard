# T049: Operator-authorized retry of a failed TP clear

## Outcome
The operator sends `/retry_tp <position_id> <reason>` on Telegram, or as a signed FCM command. That records one durable authorization. The next armed session's gate-11 recovery consumes it once. It runs at most one `TP_ATTEMPTS` sequence of take-profit PATCHes for that position, and only if the position provably came from an app buy. Nothing else is ever retried, and a buy is never resent. A refused, foreign or mismatched position gets a visible refusal and sends no PATCH.

## Why
T044 F1 deferred the automatic retry of failed TP clears. Today a `failed` tp_clears row is never retried: `pending_tp_clears` selects only `pending`/`sent`, at R:1055-1060. The position keeps a broker take-profit until a human fixes it on eToro. The T044 precheck set four conditions for any retry:
- operator authorization;
- ownership binding;
- per-run dedupe;
- a durable budget.

## Design
1. **Where it runs: inside armed gate-11 recovery, not in the command handler.** The command process holds no write-role broker client and must never send orders. The operator flow is `/resume <reason>`, then `/retry_tp <id> <reason>`, in either order. The next new-date armed session that passes gates 1-10 consumes the authorization. A dry session never consumes one.
2. **Migration 012** adds the `tp_retry_authorizations` table:
   - `id` PK;
   - `position_id` TEXT NOT NULL;
   - `command_id` INTEGER NOT NULL REFERENCES commands(id);
   - `reason` TEXT NOT NULL;
   - `status` TEXT NOT NULL CHECK IN ('granted','consumed','refused','superseded');
   - `granted_at` TEXT NOT NULL;
   - `consumed_session_id` INTEGER REFERENCES sessions(id);
   - `consumed_at`, `outcome` TEXT;
   - a partial UNIQUE index on `position_id` WHERE status='granted' (at most one live grant per position).
3. **Command `retry_tp`:**
   - Add it to `SUPPORTED_COMMANDS`. Args are `<position_id> <reason>`. The position_id must be all digits and the reason non-empty; otherwise reply with usage and create no grant. The command audit row stays `accepted`, with reason `invalid_args`.
   - Store args in `commands.reason`.
   - A position that already has a live grant gets the reply "already granted (id N)", and no second row is created.
   - The grant is a DB write only. Reply: "TP retry granted for position X; runs at the next armed session after HALT is clear."
4. **Ownership binding (before any PATCH).** Every check must hold:
   - the position's latest tp_clears row has `status='failed'`;
   - its `order_id` → orders row with `side='buy'`, a filled terminal status, and `position_id` equal to the grant's;
   - `orders.intent_id` → an intent with `side='buy'`;
   - a fresh `get_portfolio_strict()` contains the position;
   - its `instrument_id` equals `orders.instrument_id`.

   On any failure, or a portfolio read error, the grant becomes `refused` with a specific outcome. The refusal goes in followups, and no PATCH is sent. "Latest" is computed across all statuses before filtering. If the latest row is `cleared`, the grant is `refused` "already cleared". If it is `pending`/`sent`, the grant is `refused` "pending row handled by normal recovery".
5. **Consume before send.** One transaction marks the grant `consumed` with the session id and time, before the first PATCH. A crash after this never re-runs that grant: the budget is exactly one sequence per grant. It then calls `_clear_take_profit(order_row_id=<that order>, position=<live position>)`. That function inserts new rows per attempt, and the old rows are never modified.
   - Success: outcome `cleared`, added to resolved.
   - Otherwise: outcome `failed: <final detail>`, and the position is appended to `tp_failed`, so the session HALTs as today.
6. **Per-run dedupe.** `recover_unfinished` keeps `handled: set[str]` of position_ids touched in this run, by unresolved-buy recovery and by the pending-row loop. The pending loop also skips a duplicate position. The authorized loop runs last and skips any position in `handled`. That grant stays `granted`: it is not consumed and a later run may use it. Its outcome notes "deferred: handled earlier this run".
7. **Never buy.** The retry path calls only `get_portfolio_strict` and `_clear_take_profit`. Tests assert zero `place_buy_order`/`close_position` calls.
8. **Redaction:** followup and outcome text reaches T048's redaction at the session boundary. Do not put raw exception messages in `outcome`; use the type plus the tp_clears final-detail label.

## Watch

- `consume` must commit before the PATCH.
- A grant for a position that later closes must be refused, not left live forever.

- Fail-closed is the default everywhere.

## Acceptance
1. A valid grant, an owned position and a failed latest row: one sequence of at most 3 new rows, old rows unchanged, grant `consumed` with outcome `cleared`, zero buy or close calls.
2. Same setup, but the clear fails: grant `consumed` with outcome `failed`, the position in `tp_failed`, the session HALTs. A rerun on a new date does nothing for that grant.
3. Refusals, each with no PATCH:
   - a foreign position (no linked order);
   - an order side of close;
   - an order position mismatch;
   - an instrument mismatch;
   - a position not in the portfolio;
   - a portfolio read error;
   - a latest row that is `cleared`;
   - a latest row that is `pending`.
4. Dedupe:
   - a position handled by unresolved-buy recovery in the same run: grant stays `granted`, no second sequence;
   - two pending rows for one position: one sequence.
5. Crash after consume (inject before the PATCH): the next run does not retry that grant.
6. Commands:
   - a valid grant creates one row and replies;
   - a duplicate returns the existing id;
   - invalid args create no grant;
   - the FCM HMAC and replay checks are unchanged;
   - an unknown command is still rejected.
7. Dry sessions and HALTed sessions never consume a grant.
8. Migration 012 applies on a fresh DB and on an 011 DB. Both full suites pass from a baseline of 1861. `git diff --check` is clean.

## Amendments after precheck (2026-10-31, PM; latest wins)

- **F1, channel:** `retry_tp` is Telegram-only, from the private operator chat (`sender_id == chat_id`, equal to the allowlisted chat). An FCM `retry_tp` is rejected and audited (reason `channel_not_allowed`). Update the `commands.py` module and `handle()` docs: this is a new capability, an operator authorization of a broker write.
- **F2, lineage:**
  - Migration 012 adds `retry_authorization_id` (nullable FK to `tp_retry_authorizations`) on `tp_clears`. Rows from an authorized sequence carry it, so `_clear_take_profit` gets an optional `retry_authorization_id` passthrough.
  - Normal pending recovery never starts a new PATCH sequence for authorization-linked rows. It reconciles them read-only: TP absent → `cleared`; otherwise `failed`, with the position added to `tp_failed`, which HALTs.
  - An interrupted `consumed` retry (pending or sent linked rows) is reconciled read-only the same way.
  - The source intent must be `filled` or recovered-filled.
- **F3, Telegram idempotency:** a durable record of the Telegram `update_id` per processed update. A redelivered update never creates a second grant or audit-side effect. `notify/poll.py` is in scope.
- **F4, consumption:**
  - `recover_unfinished` gets an explicit `session_id` parameter, used for `consume_tp_retry`. Update the callers in `session.py`, adding `session.py` to scope for that call-site only.
  - Consumption is a guarded `UPDATE ... SET status='consumed' WHERE id=? AND status='granted'`, and proceeds only if exactly 1 row changed.
  - Environment check: the grant is consumed only when the session's `etoro.environment` equals the environment recorded on the grant at grant time. Add a `environment` column, so a demo grant is never used on real or the reverse.
- **F5, obsolete siblings:** when a grant is consumed, earlier `pending`/`sent` TP rows for that position that are not authorization-linked are durably retired (`failed`, detail `retired by retry authorization N`) in the same transaction. Test that a second new-date session does nothing further for that grant and position.
- **Ownership contract (replaces Design 4):** every check must hold.
  - The intent has `side='buy'` and status `filled` or recovered-filled.
  - The order and intent agree on session, instrument and reference/request id.
  - The order's `side='buy'` and its terminal status is a filled one: 3, 9 or 10, per `models.py` executed-fill statuses.
  - `orders.position_id` equals the grant's.
  - The session environment matches.
  - The live position is present via `get_portfolio_strict()` and its `instrument_id` matches.

  The local DB is trusted as the app's own record; this is not cryptographic proof of origin.
