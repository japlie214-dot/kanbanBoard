# T005 — S5c: gate 4 clock fails preflight when local time drifts more than 60 s from eToro

## Outcome
`gate_4_clock(...)` compares the local clock with the eToro server's `Date` header. It fails when the difference is more than 60 s, or when the header is missing or cannot be parsed.

## Why
S5 (project.md §6), smallest gate after gate 1. Session timing (T-30 alarm, hard deadline) assumes a correct clock. A drifting phone clock would place orders at the wrong time.

## Context (PM read 2026-10-01; P = `app/src/main/python/nightwatch/`)
- `P/etoro/client.py:201-203`: `self.last_server_date: str | None = None`. The comment says it is for "preflight gate 4 (clock skew > 60s aborts)". Line 326 sets it from `response.headers.get("Date", ...)` on every response.
- Format, from the test at `tests/test_etoro_client.py:1812`: RFC 7231, for example `"Fri, 02 Jan 2026 12:00:00 GMT"`.
- `P/engine/preflight.py:39`: the TODO line `4. Clock - local vs API Date header, <= 60s skew`.
- `GateResult(gate, name, passed, reason, details)` and `run_preflight` are in the same file, along with `gate_1_halt` (pattern to copy).

## Scope
- `P/engine/preflight.py`.
- A new test file, `tests/test_preflight_gate_4.py`.

## Out of scope
- The client, the host, the session and config. The 60 s limit is a keyword default, not a config field.

## Design
```python
def gate_4_clock(*, local_now: datetime, server_date: str | None, max_skew_seconds: float = 60.0) -> GateResult:
```
- Pure function. The caller (S6) passes `client.last_server_date` and `host.now()`, read right after an API call.
- Name: `"Clock"`.
- `server_date is None` → fail, reason `"no server Date header observed"`.
- Parse with `email.utils.parsedate_to_datetime`. If it raises (`TypeError` / `ValueError`) or returns a naive datetime → fail, reason `f"unparseable server Date header: {server_date!r}"`.
- `local_now` naive → `raise ValueError("local_now must be timezone-aware")`. This is a caller bug; `run_preflight` turns it into a failure.
- `skew = (local_now - server).total_seconds()`.
  - `abs(skew) > max_skew_seconds` → fail, reason `f"clock skew {skew:+.1f}s exceeds {max_skew_seconds:.0f}s"`.
  - Otherwise pass, reason `f"clock skew {skew:+.1f}s within {max_skew_seconds:.0f}s"`.
- `details`: `{"skew_seconds": skew, "server_date": server_date, "local_now": local_now.isoformat()}`. Include only the keys that are known.
- Exactly 60.0 s passes (the boundary is `>`, not `>=`).
- Add `"gate_4_clock"` to `__all__`. Change the line 39 TODO to `IMPLEMENTED below (gate_4_clock)`, matching gate 1. Change the "Gates 1, 10 and 11 are built; the other nine" docstring to "Gates 1, 4, 10 and 11 are built; the other eight", and the TODO header "(all but 1, 10 and 11)" to "(all but 1, 4, 10 and 11)".

## Plan

2. Write `tests/test_preflight_gate_4.py` with these tests:
   - 0 s → pass;
   - +59 s and −59 s → pass;
   - exactly +60 s → pass;
   - +61 s → fail;
   - −61 s → fail;
   - `None` → fail;
   - `"garbage"` → fail;
   - a naive `local_now` raises `ValueError`;
   - a local time in a non-UTC zone (e.g. `timezone(timedelta(hours=7))`) at the same instant → pass, with skew 0;
   - through `run_preflight` (as in `tests/test_preflight_gate_1.py`): gate 4 bound with +120 s, gates 1–3 passing lambdas, the rest `unimplemented_gate` → `failed.gate == 4`, and 4 rows.
