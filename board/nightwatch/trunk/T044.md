# T044 — TP-clear failure vetoes the final save

## Outcome
In an armed session, if any filled buy ends with its take-profit not confirmed cleared (`report.tp_failed`), or with no position id, the session:
- still sets HALT, as it does today;
- does **not** perform the final/day-advancing strategy-state save, and records `strategy state not saved: take-profit not cleared` in the outcome;
- keeps any UPRO checkpoint already saved earlier in the session.

At the next session after `/resume`, recovery re-attempts the clear for every still-held position whose latest TP-clear row ended `failed`. It never resends the buy.

## Why
The T042 precheck found that `session.py` HALTs on TP failure (T030) but its final-save decision has no TP veto. The day's strategy state can therefore advance as if the session completed cleanly while a position carries an uncleared broker take-profit. Separately, T029 recovery resumes only TP rows left `pending`/`sent`. A clear whose final attempt ended `failed` is never retried, so after `/resume` the TP can stay on the position silently.

## Design
1. **Veto (S:727-746).** Insert this branch after `persistence_error` and before `execution_error`:
   `elif report.tp_failed or unconfirmed: not_saved = "take-profit not cleared"`.
   - The existing later branch, "filled result has no position id", stays as it is. It is only reached if not already vetoed.
   - HALT is still raised at S:717. Bucket fills at S:718-726 are still applied, because the buy really happened.
   - The UPRO checkpoint saved earlier (T038/T042) is untouched. Only the final/day-advancing save is skipped.
   - SCHG/UPRO close effects already persisted stay persisted.
2. **Day completion.** The session row for the date exists, so a same-date rerun returns `already_ran`. No new marker is needed. The next trading date's session stops at gate 1 until `/resume`. After `/resume`, the strategy starts from the last saved state, exactly as for other not-saved outcomes.
3. **Recovery query.** Add `repo.failed_tp_clears_to_retry() -> list[dict]`. It returns one row per `position_id` (the highest `id`) where that latest row has status `failed` and its detail is not `position not in portfolio`. Rows are returned in id order. Pending/sent rows are excluded, because `pending_tp_clears` already covers them.
4. **Recovery retry.** In `recover_unfinished`, after the `pending_tp_clears()` loop, loop over `failed_tp_clears_to_retry()` and call `_recover_tp_clear`, with one change for these rows: never rewrite the old row's status. The old row is already final.
   - Read the portfolio.
   - Position absent: append to `followups`, insert no row.
   - TP absent: insert a new row through `insert_tp_clear(order_id, position_id, new_request_id(), attempt=0)` and mark it `cleared` / "confirmed at recovery".
   - Otherwise call `_clear_take_profit`. Success appends to `resolved`; failure appends to `tp_failed`, so the session HALTs again, as today.
   - Position IDs already handled in the pending loop are skipped.
5. **Never resend.** Recovery touches only TP PATCHes (`clear_take_profit`). It never calls buy/order placement, and it reads `orders` rows only for `order_id` linkage.
