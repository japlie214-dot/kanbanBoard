# T009 — S5g: operator risk limits in config, and preflight gate 12 checks that the limits are set and the open-lot cap holds

## Outcome
- `RiskConfig` gains `max_open_lots: int | None`.
- `config/config.toml` carries the operator's 2026-10-02 values.
- `gate_12_risk_caps` exists. It fails when:
  - any operator limit is unset or invalid;
  - the number of open ladder lots already exceeds `max_open_lots`.

  It reports broker take-profits as information only.

## Why
project.md §11, decided by the operator 2026-10-02:
- `max_daily_loss_usd = 500`;
- `max_notional_per_session_usd = 5000`;
- `max_open_lots = 100`;
- the lot-size check is dropped.

DESIGN.md gate table line 723. Gate 12 is the last gate buildable on the PC.

  - `__post_init__` validates notional > 0 and battery in 0..100.

  - `find_broker_take_profits(positions) -> list[BrokerTakeProfit]` (line 1071) is detection only.
  - Its docstring records that 229 of 230 live positions carry a broker TP at multiple 11.00 (legacy, adopted positions). Whether eToro applies its default TP to API-opened positions is **unresolved** (preflight.py:1076–1080, DESIGN.md:978–982; precheck 2026-10-02 contradicts project.md's 'settled by T6'). **Either way, a broker TP must never fail gate 12.** 229 legacy positions carry one, so a TP failure would fail every session forever.

By design (DESIGN §5; session.py is still a TODO), preflight runs before the session decides any order, and no daily P&L computation exists. They belong to the S6 executor and a separate ticket. Gate 12 checks here only that both are **configured** (DESIGN_session's arming-completeness rule, project.md §6 S6 line 274).

## Scope

  - add `max_open_lots: int | None = None` to `RiskConfig`;

  - the loader reads `max_open_lots` the same way as `max_daily_loss_usd` (`None`/`""` → `None`, else `int(...)`).
- `config/config.toml` `[risk]` (the `max_daily_loss_usd` comment becomes "daily loss ALERT threshold; never halts (T010)"):

## Out of scope
- Computing daily P&L, or enforcing notional per order (S6 / a later ticket).
- Any lot-size check (dropped by the operator).
- Gates 2 and 3. Android files. `secrets/`, `config/.secrets.env`.

## Requirements
1. `gate_12_risk_caps(*, risk: RiskConfig, repo: Repo, positions: Sequence[Position]) -> GateResult`, number 12, name `"risk_caps"`.
2. If `risk.max_open_lots` is None, fail with reason `"risk limits unset: max_open_lots"`. `max_daily_loss_usd` is an **alert threshold only** (operator decision 2026-10-02, T010). Gate 12 never fails on it, set or unset. Report it in details. `max_notional_per_session_usd` is never None.
3. `open_lots = len(repo.list_lot_annotations(is_open=True))`. If `open_lots > risk.max_open_lots`, fail with reason `f"{open_lots} open lots exceed max_open_lots {risk.max_open_lots}"`. Equal to the cap passes. Blocking a new buy at the cap is the executor's job.
4. `tps = find_broker_take_profits(positions)` is information only. It never changes `passed`.
5. Pass with reason `"risk caps ok"`. `details` (also on failures, wherever computed so far):
   - `max_notional_per_session_usd`, `max_daily_loss_usd`, `max_open_lots`;
   - `open_lots`;
   - `broker_take_profit_count`: `len(tps)`;
   - `evaluated_elsewhere`: `["max_notional_per_session_usd", "max_daily_loss_usd"]`, so the report never implies those were enforced here.
6. No network calls, no DB writes.

## Design
- `RiskConfig` stays the single home for the caps. The gate reads it; it does not re-parse config.
- `positions` is injected (S6 fetches them once for gates 11 and 12), so the gate makes no client call.
- `max_daily_loss_usd` does not gate anything (T010: report and alert, never halt). Its `RiskConfig` docstring and the `config.toml` comment must say "alert threshold; never halts".
- `max_open_lots` defaults to `None` in code. An old config without the key then reports "unset" in gate 12 instead of silently getting a made-up number.
