# T052: Bound the remaining recovery and notification waits

## Outcome
The waits that T050 left out of scope behave predictably. A loop that is confirming an order already sent keeps its own bound and never gives up early because of the session cutoff. Instead, it stops cleanly once the client's T050 deadline makes every further read fail, and leaves the intent unresolved for the next run. No loop sleeps after its last attempt, and no sleep overshoots its own bound. Telegram never sleeps longer than a fixed cap on one Retry-After.

## Why
- The T050 precheck (2026-11-06) listed these loops as reachable before orders but outside T050's scope.
- Since T050, the eToro client raises `EtoroTimeoutError` (reason `deadline`) on every read once close-25 has passed during preflight and recovery. The polling loops below swallow those errors and keep sleeping. Recovery after the cutoff can therefore burn up to ~21 s per TP read-back and ~30 s per position read, all on reads that cannot succeed.

## Context (HEAD 21c06ba, re-read 2026-11-06)
Short names: E = `etoro/client.py`, X = `engine/executor.py`, C = `engine/close_executor.py`, N = `notify/telegram.py`. All are under `app/src/main/python/nightwatch/`.
- **T050 deadline API:**
  - E:199 `self._deadline`; E:239-240 `set_deadline_in`.
  - E:242-246 `_check_deadline(wait)` raises when expired or when the wait would cross the deadline.
  - E:248-250 `_sleep_with_deadline`.
  - There is no public read-only accessor yet.
- **`poll_order_to_terminal`** (E:2053-~2100): sleeps `interval` at E:2093 after checking its own monotonic timeout. It does not clamp `interval` to the time left, so it can overshoot `timeout` by up to one interval. Default 2 s interval, 90 s timeout. It is reached from buy recovery and full-close recovery.
- **`_read_position`** (X:114-122): `READ_TRIES = 10`, `READ_SLEEP = 3.0` (X:45-46). It sleeps after every miss, **including the last**, so 3 s are wasted per exhausted read. `_portfolio_position` (X:104-111) swallows every exception, including the T050 deadline error, so an expired deadline turns into 10 misses and 30 s of sleep.
- **TP read-back** (X:157-163): `TP_READBACK_TRIES = 7`, `TP_READBACK_SLEEP = 3.0` (X:43-44). It sleeps before each read and swallows errors the same way.
  - After the deadline expires, the next PATCH attempt in `_clear_take_profit` already fails on the T050 check, as a write with zero attempts. It is caught as `error:`, and the loop continues to the next attempt, which fails the same way. That cost is bounded and harmless, but noisy.
- **Full-close confirmation** (C:110-141): `for attempt in range(10)`. It checks `deadline` before each read and clamps the sleep to the time left (C:141), so the sleep is already correctly bounded.
  - Recovery passes `datetime.max` (C:518), so in recovery the bound is 10 reads with 9 sleeps of 3 s. Strict-read errors are swallowed (C:117).
- **SCHG close lookup** (C:314-354) and **SCHG portfolio confirmation** (C:358-392): both use windows clamped to `deadline` (60 s / 90 s) with clamped sleeps. Recovery passes a fresh `now + 150 s` (C:476).
  - A lookup failure other than 404 ends the lookup at once as `unresolved` (C:320-321); a T050 deadline error is not a 404, so the lookup already exits immediately.
  - Portfolio errors are swallowed (C:362-363).
- **Telegram `_send_one`** (N:205-251): `_MAX_ATTEMPTS` with backoff capped by `_MAX_DELAY_SECONDS` (N:288-290). **A 429 sleeps the parsed `retry_after` uncapped** (N:240, N:269-286). There is no session deadline, by design: alerts must still go out after the cutoff.

## Per-loop decision
| Loop | Bound by close-25? | Decision and reason |
|---|---|---|
| `poll_order_to_terminal` (E) | **No** | It confirms an order already sent; abandoning it early leaves a real broker order unknown. Keep the own timeout. Only clamp each sleep to `min(interval, deadline_own - now)`, and do not sleep when that is ≤ 0. If the T050 deadline raises inside a lookup, let it propagate as today. Fresh execution treats a raised poll as unresolved; buy recovery passes it to the existing `_age_or_abandon` (see Amendment F1). |
| `_read_position` (X) | **No new bound**, but stop wasting time | It confirms a filled buy's position. (1) No sleep after the final try. (2) If the client reports its deadline expired, return `None` immediately (no more reads or sleeps). The caller's existing "no position" path applies: a recovered pending fill stays pending for the next run; a fresh buy already filled stays resolved and reports `tp_failed` (see Amendment F2). |
| TP read-back (X) | **No new bound**, but stop wasting time | Before each read-back sleep, and before each new PATCH attempt, stop if the client deadline has expired. Mark the row `failed` with the fixed detail `deadline: read-back not attempted` or `deadline: attempt not started`. The function returns False, so per T053 the position goes to `tp_uncleared`: alert only. An attempt already sent is never resent. |
| Full-close confirmation (C:110-141) | **No** | It confirms a sent close. Keep its own 10-read bound. Add an early exit when the client deadline has expired: `uncertain("deadline: confirmation paused")`, which leaves the intent unresolved. Do **not** replace `datetime.max`; recovery must not invent a cutoff for a sent close. |
| SCHG lookup / portfolio (C) | **No** | They confirm a sent close and already stop at their window or deadline. Add the same early exit in the portfolio loop. The lookup loop already exits on non-404 errors. |
| Telegram 429 (N) | **No** (alerts must go out) | Cap one 429 sleep at `_MAX_DELAY_SECONDS`. If Telegram asks for longer, sleep the cap and let the next attempt run; after `_MAX_ATTEMPTS`, raise as today. Network and 5xx backoff are unchanged. |

**Invariant:** none of these changes makes a sent order look resolved, abandoned or failed at the broker. An early exit only ends this run's waiting. Pending order confirmations stay for the next run; failed TP rows are deliberately not retried; already-filled buys stay resolved (see Amendment F2). No new write is ever started after the T050 deadline.

## Acceptance
1. `poll_order_to_terminal` with an own timeout of 5 s and an interval of 2 s never sleeps past 5 s in total. When the time left is 0, it returns `timed_out=True` with no further sleep. With no T050 deadline set, results stay equivalent to the baseline because of the final status read (Amendment F1).
2. `_read_position` with all misses makes 10 reads and 9 sleeps (not 10). With the client deadline expired, it makes 0 further reads and 0 sleeps and returns `None`.
3. `_clear_take_profit` with the deadline expiring during read-back stops with no further sleeps or reads. The row is `failed` with the fixed `deadline:` detail, no new PATCH attempt starts, and the function returns False. A test confirms that in a session this yields T053 alert-only handling: no HALT, `tp_uncleared` set.
4. Full-close recovery, split by when the deadline expires:
   - (a) Expired before polling: the result is `close poll failed: EtoroTimeoutError: deadline`. This is existing behaviour and stays unchanged.
   - (b) Expired during portfolio confirmation: the result is `unresolved` with detail `deadline: confirmation paused`; the intent stays unresolved and no new close is sent.
   - Durable evidence confirmed earlier may still be applied (C:489-499); that is preserved.
5. The SCHG portfolio loop with the deadline expired exits at once as unresolved. The lookup loop is unchanged.
6. Telegram 429 with `retry_after = 600` sleeps at most `_MAX_DELAY_SECONDS` per attempt, and on exhaustion makes 5 attempts with 4 capped sleeps, as today. 4xx stays permanent.
7. With no deadline set, every existing recovery and close test passes unchanged apart from the documented sleep-count updates.
8. Both full suites pass from a baseline of 1980. `git diff --check` is clean.

## Amendments after precheck (2026-11-06; latest wins)
- **F1, recovery abandonment.**
  - A buy-recovery poll that raises or ends nonterminal reaches the existing `_age_or_abandon` (X:587-600, X:520-523). At the age threshold it abandons the intent, even on a deadline error. That is existing behaviour.
  - Requirement: the clamp must not cause an earlier abandonment than the baseline. When the clamped poll reaches its own timeout, it does one final status lookup at the timeout before returning `timed_out`. That read covers the status the old overshoot read would have seen.
  - New acceptance 9: a threshold-aged sent buy in recovery whose broker status turns filled between the new clamped endpoint and the old overshoot point ends filled, as in the baseline, not abandoned.
- **F2, what happens next run.**
  - A pending order confirmation (a sent buy or close that is still unresolved) stays pending for the next run.
  - Failed TP rows, including the new `deadline:` rows, are intentionally not retried (T053 policy; R:1055-1060 selects only pending/sent).
  - Fresh buys already marked filled stay resolved (X:387). A missing position there reports `tp_failed`.
- **F3, timing.** The poll clamp changes timing at the edge of its own timeout even with no deadline set. With the F1 final read, the observed results stay equivalent to the baseline.
- **F4.** Acceptance 4 is split into (a) expiry before polling (unchanged) and (b) expiry during portfolio confirmation (new early exit). Applying durable evidence confirmed earlier is preserved.
- **Labels and redaction.**
  - Persisted TP-row details go to the DB directly (R:1579-1594), not through T048 redaction. They are fixed labels with no interpolated data.
  - The TP early-exit check runs again after each read-back sleep, so a deadline that expires during the sleep does not trigger another portfolio read.
- **Tests.** The notifier tests go in `tests/test_notify_telegram.py`. On Telegram exhaustion, the expected result is 5 attempts and 4 capped sleeps.
