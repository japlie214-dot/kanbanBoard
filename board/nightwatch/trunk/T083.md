# Outcome

From the protected monitor, request a fresh, read-only demo broker account/positions/open-orders check or pause new demo submissions. Reopening the page must show whether Z10 actually applied the request. Never cancel an open order, close a position, resume, or submit an order through these controls.

## Evidence and release gates

- Link the operator request, expiry, Z10 acknowledgment and snapshot or pause result by stable request ID. Show send failure, pending, applied, expired/unconfirmed separately. An expired request is not proof that an order could not have been sent. Receipt time alone is not broker observation time.
- Authorize writes independently of the snapshot read token. Constrain accepted actions and device environment. Reject stale or duplicate execution, real-account requests and unsupported clients. A generic command passthrough is not this interface.
- Refresh must perform read-only reconciliation, not invoke the strategy. Missing/partial broker responses stay explicit. Pause must survive restart and gate the final new-order submission path; in-flight and open orders are not retroactively canceled.
- Verify synthetic failure, offline, replay, expiry and enforcement before enabling controls. Require one verified demo APK and an observed correlated device round trip before a live acceptance claim. Do not test pause by submitting an order.

## Design — first verified slice

Implement a storage-independent receipt reducer in `cloud/worker/src/demo-control-receipt.js` and tests in `cloud/worker/test/demo-control-receipt.node.mjs`. Not an endpoint. Accept only `refresh_demo_broker` and `pause_demo_orders`, explicit demo mode, a UUID, a known device capability, verified operator write authority (never infer from a reader), and finite timestamps. Give requests a 120-second execution deadline. Derive pending/expired-unconfirmed on read. Accept only authenticated same-ID/action/device/environment acknowledgments; require broker observation after issue covering account, positions and open orders for refresh, or persisted pause plus final submission guard evidence for pause. Carry no raw broker records. Reject future/invalid times, reject late execution, allow late reporting of timely execution, make accepted terminal transitions immutable. Keep server-owned authority and device-proof flags separate from untrusted request payloads. No network, binding, npm install or dispatch in this slice.

## Plan and Prove

1. Add synthetic negative/boundary tests for both actions, unknown environment, read-only authority, missing capability, deadline, forged or mismatched receipts, non-durable pause, partial broker refresh, duplicate and late reports.
2. Implement pure, JSON-serializable request/transition/status functions. Use round-trip serialization in tests to prove reload semantics of the record, not persistence of a deployed backend.
3. From repository root run `node --test cloud/worker/test/demo-control-receipt.node.mjs` and `git diff --check -- cloud/worker`. No generated files or test output on disk. Do not claim a persistent store, control endpoint or device worker until subsequent slices are implemented.

## Integration and device acceptance

The 14 local receipt tests passed. The reducer alone is not a device capability. Build, device, and cloud work now proceed as disjoint changes; no production dispatch until they agree on the authenticated wire contract and pass negative tests. Do not ship an APK that disables the existing unattended demo pathways as a substitute for credential-free compilation. Signing must preserve the current install, without exporting or inspecting private signing material.

On Z10, verify (1) an explicitly demo-only read after the request, including broker observation time and complete account/positions/open-order evidence, and (2) a persistent pause verified after restart using a non-transmitting submission check through the same guard used for real submissions. Never make a test order or use the presence of zero submissions alone as proof. No clearing pause, cancellation, or closing positions under this goal. Report any component that cannot be verified separately.

## Local receipt interoperability proof

A disposable Java/JCA signer generated an ephemeral RSA keypair in memory and separately encoded both v1 receipts from synthetic constants. The actual Worker `verifyDeviceReceipt` accepted both JCA signatures using only the public key and rejected no required field as missing. This checks JVM-to-Worker wire compatibility, not Kotlin/Android execution, hardware-backed key storage, device provisioning, operator authorization, authenticated dispatch or a Z10 broker observation. No actual device key or broker data was used. Do not deploy the new Pages middleware without its verifier binding.
