# T003 — S5a: `run_preflight` orchestrator runs gates 1–12 in order and fails closed

## Outcome

It stops at the first failure, persists one `preflight_checks` row per gate it ran, and returns a single outcome that names the failing gate. A gate that is not built yet fails, with reason `not implemented`. The existing gates 10 and 11 get an orchestrator that the session can call (wiring, not new callables).

## Requirements
1. `run_preflight` runs gates in ascending gate number. The first gate whose result has `passed=False` stops the run, and no later gate runs.
2. A gate that raises an exception counts as failed. Its reason is `f"exception: {type(exc).__name__}: {exc}"`. The exception does not propagate. No later gate runs.
3. Every gate that ran, whether it passed, failed or raised, gets exactly one `preflight_checks` row via `repo.record_preflight_check`. Field mapping:
   - `gate`, `name` and `passed` from the result;
   - `detail` = `json.dumps({"reason": reason, "details": details}, default=str, sort_keys=True)`.
   Gates that did not run get no row.
4. The gate list must contain gates 1..12, each exactly once. If it does not, raise `ValueError` before any gate runs and write no rows.
5. Each gate's result must report its own number (`result.gate == spec.number`). A mismatch counts as a failure, with reason `f"gate {spec.number} returned result for gate {result.gate}"`.
6. `unimplemented_gate(number, name)` returns a `GateSpec` whose check returns `GateResult(number, name, False, "not implemented")`.
7. The return value is a `PreflightOutcome` with:
   - `passed` (True only if all 12 ran and passed);
   - `results` (one per gate that ran, in order);
   - `failed`: the failing `GateResult`, or `None`.

## Design
Add the following to `P/engine/preflight.py`, after `GateResult`:
```python
GateCheck = Callable[[], GateResult]

@dataclass(frozen=True)
class GateSpec:
    number: int
    name: str
    check: GateCheck

@dataclass(frozen=True)
class PreflightOutcome:
    passed: bool
    results: tuple[GateResult, ...]
    failed: GateResult | None

def unimplemented_gate(number: int, name: str) -> GateSpec: ...

def run_preflight(gates: Sequence[GateSpec], *, repo: Repo, session_id: int) -> PreflightOutcome: ...
```
- Each gate is a zero-argument closure. The caller (S6) binds each gate's inputs (positions, rates, config) when it builds the list. Why: the gates have very different inputs, so the orchestrator stays one job (order, stop, persist), and it is testable with plain lambdas. A future gate never changes the orchestrator (open/closed).
- `Repo` import: `preflight.py` already imports from `nightwatch.db.repo` at module level (lines 121–122); add `Repo` and `PreflightCheck` to that import. No cycle (precheck read).
- No default gate list in this ticket. S6 builds it.

## Plan
1. In `preflight.py`, add `GateCheck`, `GateSpec`, `PreflightOutcome`, `unimplemented_gate` and `run_preflight` as in the Design.
2. `run_preflight` steps:
   1. Validate the numbers (`sorted(numbers) == list(range(1, 13))`). If that fails, raise `ValueError`.
   2. Iterate the specs sorted by `number`.
   3. Call `check()` inside try/except `Exception` and apply Requirement 5.
   4. Record the row.
   5. On failure, return immediately.
3. Write `tests/test_preflight_orchestrator.py`, using the `repo` fixture and a session from `repo.create_session` (signature in Context). It needs at least these tests:
   - all 12 pass: `passed` True, 12 rows in gate order;
   - gate 3 fails: rows for 1–3 only, `failed.gate == 3`, and a counter shows gates 4–12 never called;
   - gate 5 raises `RuntimeError("boom")`: a row with `passed` 0 and a reason starting `exception: RuntimeError: boom`, and no later gate called;
   - a list with a missing gate or a duplicate: `ValueError` and zero rows;
   - gates given out of order are run in ascending order;
   - a gate returning the wrong `gate` number fails;
   - `unimplemented_gate(7, "environment")` fails with `not implemented`;
   - a real gate 11 (`gate_11_reconciliation` with empty positions and annotations, bound in a lambda) runs through the orchestrator and its result is persisted. This proves the wiring is not just a mock.
   - the `detail` JSON round-trips `reason` and `details`.
4. Run Prove.
