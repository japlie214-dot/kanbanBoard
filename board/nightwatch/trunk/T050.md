## Outcome
In an armed session, once the close-25 cutoff has passed, the bounded loops start no new transport attempt and no new sleep. The bounded loops are the eToro `_request`, eToro `_wait_for_capacity`, Tiingo `_request` and the preflight network retry. Instead they raise right away. The raised error goes through whichever existing session handler applies to that phase. No handler or status changes.

## Why
This was deferred from T047. T047 bounds the session's outer market-data retry. The inner loops still back off on their own and honour Retry-After without limit. A single call can therefore sleep past close-25.

## Context
- eToro `_request`, `etoro/client.py:307-362`:
  - it retries reads;
  - write attempts are limited to 1 (`:305`).
- eToro `_wait_for_capacity`, `etoro/client.py:238-246`:
  - it runs before every transport attempt (`:308`);
  - it has a 120 s safety valve and is not tied to close-25.
- Tiingo `_request`, `market/source.py:280-320`:

- Preflight network retry, `engine/preflight.py:254-290`:
  - it is wired by `session.py:148-150`;
  - it has a 90 s elapsed budget and no close-25 check.
- Existing client clocks are monotonic floats, not datetimes:
  - `client.py:162,198`;
  - `source.py:208`.
- Existing pre-order statuses differ by phase. They stay as they are:
  - preflight read failure gives `preflight_failed` (`preflight.py:493-526`, `session.py:534-536`);
  - a market-data failure gives `market_data_failed` (`session.py:550-570`);
  - a Tiingo history failure gives `signal_failed` (`session.py:586-593`);
  - a portfolio or balance failure gives `decide_failed` (`session.py:600-604`);
  - otherwise the session's fallback at `:921-924` gives `aborted_before_orders`.

  - zero order rows therefore do not prove that no write happened;

## Design
- **Deadline API.** Both clients, and the preflight retry, get `set_deadline_in(seconds: float | None)`:
  - `None` clears the deadline;
  - otherwise the deadline is stored as `self._clock() + seconds`, using that object's existing monotonic clock. Preflight uses its own injected clock or `time.monotonic`.
  - The default is no deadline, so behaviour is unchanged when nothing is set.
- **Session.** Before preflight, the session computes `seconds_remaining = (cutoff - now_utc).total_seconds()`:
  - `cutoff` is close-25 and `now_utc` is the session's UTC clock;
  - the session passes the value to the eToro client, the Tiingo source and the preflight retry;
  - it calls `set_deadline_in(None)` on each before any order send.
- **Before each attempt.** If the deadline has passed, raise the class's existing timeout error with the redacted reason `deadline`:
  - eToro raises its timeout error;
  - Tiingo raises its timeout error;
  - preflight raises its existing network or timeout failure.
- **Before each sleep.** Clamp the sleep to the remaining time:
  - if the remaining time is ≤ 0, or a full sleep would cross the deadline, raise the class's typed error for the last failure instead of sleeping (or raise the timeout error with reason `deadline`);
  - this applies to backoff, Retry-After and capacity waits;
  - the preferred choice is to raise rather than sleep partway.
- **Capacity wait.** `_wait_for_capacity` checks the deadline before each chunk.
- **Writes.** Write requests stay at exactly 1 transport attempt. The deadline never adds a retry.
- **Handlers.** No new statuses and no handler changes. The error surfaces through whichever existing handler applies.

## Ripple effects
- Error types are unchanged, so existing handlers apply.
- If the deadline is left set after the order phase, post-order reads would be cut short. The design clears it before sends. A test asserts that a read still retries after the deadline is cleared.

## Watch
- `Retry-After=None`.
- A negative `seconds_remaining` at set time: the next attempt must raise immediately.
- The capacity-wait 120 s safety valve must still work when no deadline is set.

## Acceptance
- eToro read, deadline 5 s ahead, a 5xx and then a backoff longer than 5 s: the call raises a typed error. No sleep crosses the deadline, and no attempt starts after it.
- Tiingo read, the same setup: the same result.
- A Tiingo 429 with Retry-After=600 and the deadline 60 s ahead raises without sleeping 600 s.
- Deadline already expired: the first eToro or Tiingo attempt raises the timeout error with reason `deadline`, and the transport is never called.
- `_wait_for_capacity` with the buckets exhausted and a deadline: no sleep chunk crosses the deadline, and the call raises.
- Preflight network retry with a deadline: no retry wait crosses the deadline.
- No deadline set: retry counts and sleeps are identical to before, and the existing tests pass unchanged.
- In an armed session test, retryable failures across close-25 end through the existing handler for that phase. In the bounded loops, no transport attempt or sleep starts after the deadline. The test asserts the exact status that the phase handler produces.
- Write requests stay at 1 transport attempt with or without a deadline. The bounded loops never retry a write.
- `set_deadline_in(None)` before sends: a later read retries as before.
