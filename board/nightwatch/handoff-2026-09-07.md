## 1. The lessons — most important part of this document, read in order

### Lesson 0 (new today): the reported test count was wrong, and the reason is itself instructive

`HANDOFF_2026-09-06.md` reported "550 → 671 passing, zero failures." Running
`.venv/Scripts/python.exe -m pytest -q` today reproduces **670 passed, 1 failed** —
`tests/test_order_budget.py::test_using_the_placeholder_logs_an_error_not_silence` fails with
`assert False` on `any("PLACEHOLDER" in record.message for record in caplog.records)`.

The test **passes in isolation** (`pytest tests/test_order_budget.py`) and passes when run after
itself in any order that doesn't include the culprit. It only fails as part of the full default
suite, because **some earlier-run test file calls `configure_logging()`, which sets the `nightwatch`
logger's `propagate = False` globally**, and nothing undoes it. `caplog`'s default handler is
attached at the root logger, so once propagation is off, records from `nightwatch.engine.order_budget`
never reach it — `record.message` is never populated, and the assertion sees an empty record list.

**This is not a fresh discovery — it is a known trap, already worked around twice in this same
codebase**, by two different test files, each with an explicit comment: `tests/test_market_bars.py`
(`_capture_bars_logs`) and `tests/test_notify_telegram.py`
(`test_disabled_when_secrets_absent_never_raises`) both attach their own handler directly to the
module logger *specifically because* "another test module may have set `nightwatch.propagate =
False` via `configure_logging()`... which would otherwise silently stop records from this module
reaching caplog when the full suite runs." `tests/test_order_budget.py` was written the same day as
those comments already existed elsewhere in the suite, and did not apply the same defense.

**The general rule this adds, in the same family as HANDOFF_2026-09-06 §1's three instances:** a
green run and a *reported* green run are not the same fact, and neither is checkable by reading a
handoff — only by running the suite yourself, in its default order, the way CI would. A test that
passes in isolation and is asserted to pass as part of "671 passed" without anyone having actually
run the full default invocation is exactly this project's own pattern one level up: a plausible
number, trusted by association, sitting next to the real one. **Verify a test-count claim by
running the suite once, exactly as the next agent will, not by re-running a subset.**

This is **not a `.py` fix** (this document's own scope is docs-only) — flagged here, and separately
below (§9 to-do list) as a fix for whoever next touches `.py` files: either give
`test_order_budget.py`'s caplog-based tests the same directly-attached-handler treatment already
used twice elsewhere, or make `configure_logging()` restore `propagate` in a fixture teardown so it
stops leaking across test modules. The second is the more general fix — the first is a per-symptom
patch that a third and fourth test file will eventually need again.

**Gotcha, this session, now fixed:** `caplog`-based log-content assertions in this codebase used to
be reliable only when run in isolation, or when the test attached its own handler directly to the
module logger — see §1 lesson 0. As of the same-day fix, `tests/conftest.py`'s
`_restore_logging_state` autouse fixture restores the polluted global logging state after every
test, so this is no longer a trap a new test file needs to know about. Left here as a record of why
that fixture exists, not as a live warning.

**New gotcha, this session, still current: this repo has two Python interpreters and they can
disagree about whether the suite is green.** `python -m pytest -q` (system Python) and
`./.venv/Scripts/python.exe -m pytest -q` (the repo's own venv) collect and order tests
differently, so state that leaks between tests (like the `configure_logging()` propagate leak
above) can bite one interpreter's ordering and not the other's. **A green reading from only one of
them is not evidence the suite is green** — this exact test-isolation bug was invisible under
system Python (671 passed) and only surfaced by running `.venv` too (670 passed, 1 failed). Treat
`.venv` as authoritative, but run both, every time, and report both numbers; a claim checked against
only one interpreter is the same kind of unverified claim §1 lesson 0 already warns against.
