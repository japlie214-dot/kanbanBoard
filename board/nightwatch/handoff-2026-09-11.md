# etoroNightwatch — Handoff: the live window, and four parsers that were never right

**Date:** 2026-09-11 (Friday, the live window)
**From:** the session that ran the 2026-09-11 market window as overseer over subagents.
**To:** whoever builds `run_preflight()`, `engine/session.py`, or the SCHG executor next.

Supersedes `HANDOFF_2026-09-07.md` where they disagree.

**The headline is not the latency number.** The latency measurement was the stated point of the
day and it was **not obtained**. What the attempt found instead is that the order lifecycle was
non-functional end to end: four separate parsers read live payloads against guessed shapes, and
every one failed *silently*. The app could not confirm a fill, could not learn a position's id,
could not size a partial close, and could not confirm a close. All four would have surfaced on the
first live session against the real account. They surfaced today against demo, for $0.

---

## 1. The lesson

**A parse miss that produces a plausible value is worse than a crash.** Every defect below shares
one shape: a lookup against an assumed key, whose failure is indistinguishable from a legitimate
result.

- `_parse_order_result`: `row["status"]` is really `{"id":3,"name":"Filled"}`. `int(dict)` raises,
  the exception is **caught**, and the status silently becomes `RECEIVED`. An order that filled in
  **163 ms** was polled for 90 s and declared a timeout.
- `_parse_order_result`: `row["positionId"]` is really at `positionExecutions[0].positionId` →
  `position_id=None` → the position can never be closed. This is what stranded demo positions.
- `_parse_order_result`: `row["units"]` — **no `units` key exists**; it is `requestedUnits`. This is
  the exact field the partial-close leg depends on, flagged as an unverified assumption in the
  morning's offline rehearsal and confirmed broken in the afternoon.
- `close_position` (`client.py:1179-1180`): `data.get("orderId") or ... or data.get("id")` matches
  nothing real → empty order id → the confirming lookup 400s with *"Either orderId or referenceId
  must be provided"*. **Every close the app issues is fire-and-forget.**
- `_detect_environment`: scanned for keys absent from the `/balances` body and returned `None`
  unconditionally, making **`verify_environment()` a silent no-op in production — on the real
  account as much as demo**. The app's environment guard never guarded anything.

The same disease appeared in the tooling: the latency harness printed *"Cleanup confirmed: no DEMO
position left open"* after an order that had timed out but could still have filled; and a later run
reported one stranded position when there were two. `HANDOFF_2026-09-07.md` §1 lesson 0 warned that
a reported green and an observed green are different facts. Today produced five more instances.

**Rule to carry forward:** a field that cannot be parsed must raise or be visibly absent. Never
substitute a default for a value you failed to read.

## 4. The book, as it actually is

- **230 open real positions.** 10 UPRO lots, $6,500 basis, 43.666382 units.
- **Three UPRO lots are $1,000 — double the $500 standard**, and the operator confirms this was
  **intentional**. The book is no longer uniformly sized.
- **229 of 230 positions carry a broker-side take-profit at 11× entry** and none has an effective
  stop. The broker declares `defaultTakeProfitPercentage: 1000.0` for exactly the config Nightwatch
  orders into. One position (`3550406905`) has `isNoTakeProfit: true`, proving suppression is
  representable. **Whether API-placed orders inherit the default is UNKNOWN** — all 230 were placed
  by hand through the app.
- **The local DB knows none of this.** `data/nightwatch.db` is at `schema_version=1 (baseline)`,
  `lots` is empty, and `lot_annotations` **does not exist** — migrations 002–007 were never applied
  locally.

**Heterogeneous lot sizing audit — the built code is clean.** Every dollar decision in
`strategy/ladder.py` sums per-lot `cost_basis` or `units × price`; adoption matches on a *relative*
tolerance (`reconcile.py:389`) and on `position_id`, never on an expected size; `config.py` has no
lot-size constant. Corrections to assumptions made mid-session: the sell-to-target loop and HCBF
selection **do not exist in code at all** (spec only; `executor.py`/`session.py` are stubs), and
`lot_annotations` **does** have `entry_amount` — what it lacks is `units` and a mutable *current*
amount. Three consequences:

1. **`strategy/min_allocation.py:261`** — `floor(budget / order_size)` is the only
   dollars÷constant→lot-count in the codebase. Surfaces as *"Affords N of 60 ladder rungs"*, which
   describes a uniform book that is not the operator's. **Wrong number, display-only** — never gates
   an order. Fix the claim, not the arithmetic.
2. **`max_lots = 60` is now permanently slack.** It was co-calibrated with `order_size = budget/60`;
   on $1,000 lots the dollar ceiling binds at ~30, so the count cap can never fire. Harmless, but
   the implied "these two 60s are the same 60" invariant is false, and
   `order_budget.assert_plausible_intent_count`'s ceiling is looser than intended.
3. **Mixed sizing improves re-link uniqueness.** The split re-link key is `(instrument_id,
   entry_date, entry_amount)`; the live book already holds two UPRO $500 lots opened the same day,
   surviving only because `entry_date` keeps a full timestamp.

`DESIGN_session.md` §4.9 already opens with *"Do not assume uniform $50 lots"* — the unbuilt
executor's spec is heterogeneity-aware. But §4.4's stated *reason* for rejecting a total-cost-basis
sort ("every one opens at exactly $50 and therefore ties") is now false and should be re-derived
rather than cited. `order_budget.py:18-20` describes the book as bimodal; it is trimodal.
