## 1. The lesson this session added

The previous handoff's lesson was that a green suite is evidence about your fixtures, not about
eToro. This session added a second failure mode of the same family, found in our own new work:

**A safety mechanism was built, tested, marked done — and was inert.** The §3a ATH floor was
implemented with an empty-sequence default and **no production caller**. It passed its tests. It
appeared complete on the TODO list. It would never have engaged.

It is now a **required** argument: omitting it is a `TypeError`, with tests that fail if anyone
reintroduces a default. The general rule earned here: **check that a new guard has a live caller,
not just tests.** A mechanism nothing calls is indistinguishable, from the test suite's point of
view, from one that works.

A third instance appeared in documentation: after the window decision changed, the previous handoff
still marked both bugs "unfixed" and named an aborted decision as current. A handoff that disagrees
with the code is the same pathology in prose — a plausible statement beside a real one, trusted by
association. Reconciling docs after a reversal is not tidying; it is the same class of work.

## 3. Bandwidth was never the constraint

The 39-month window existed to conserve bandwidth. Tiingo's actual free tier, from the operator's
dashboard: **1 GB/month, 1000 requests/day, 50/hour, 500 symbols/month.**

Measured, not estimated: full history from 2010 is **4,194 bars / 1.10 MB** — about **33 MB/month,
3.2% of quota**, growing ~2.5 MB/month per year. The docs had been sizing against the *request*
quota (`DESIGN_market_data.md:537`) while the real limit is bytes, and the bandwidth figure appeared
nowhere. That is how a window got shortened to save something that was never scarce.

So: fetch full history, and obey `DESIGN_market_data.md` §2.2 outright — one fetch, one adjustment
epoch, zero persisted state — instead of arguing around it. §7's "is 39 months enough?" is closed
for the live app.

**The staircase (`DESIGN_ath_staircase.md`) is designed and deliberately unbuilt**, as insurance if
Tiingo shrinks the free tier. Its argument against §2.2's prohibition is narrow and worth preserving:
once ATH uses **raw** close, the stale-adjustment-epoch objection dies because raw closes are never
retroactively revised; and a max over a closed past interval is a **pure function of history**, so
storing it is a *cache* (re-derivable, verifiable), not *accumulated state* (drifting, uncheckable).

## 4. `entry_tier` is write-only — and it changes what the migration is for

Verified by grepping the whole package: **`entry_tier` is stamped and serialised but read by NO
decision.** The buy-budget gate uses the continuous

```
lot.entry_reference_spy / current_ath - 1.0
```

— SPY's raw close on the lot's open date, against today's ATH, recomputed every bar.

Consequences:

- What the migration must reconstruct correctly is a **price lookup**, exact from full history since
  2010 — not an inferred tier.
- Its errors are **continuous, not discrete**. There is no tier cliff to fall off.
- §3a's halt-vs-guess design matters for **provenance and reporting**, not for money.

**Direction of harm** (the question §3a could not answer while `ladder.py` was a stub): a lot
recorded **too deep** escapes the budget count at intermediate tiers, so the strategy permits more
buying than the calibrated schedule intends — real capital over-committed. **Too shallow** only ever
makes it more conservative. This **confirms** §3a's tier-0-over-tier-1 default, which had been
recorded as a disagreement with the operator's initial suggestion.

**Caveat:** true of the ladder *as ported today*. If future exit logic ever reads `entry_tier`, it
becomes load-bearing retroactively — which is what `entry_context_source` exists to protect.


All 227 open dates resolve to a real SPY bar, **zero fallbacks**. Oldest position **2024-08-21** —
~14.6 years of margin above the 2010 floor. The previous handoff's fear that 72 of 202 SCHG
positions would be stranded is comprehensively dead.

**Do not run it for real yet, and the reason is sequencing, not data quality.** There is **no
sidecar database on the device at all** (both app-private storages checked). A real write today
means a laptop script creating a database from scratch and hoping the app adopts that exact file.
The backfill is meant to be the app's own one-shot bootstrap, on-device, against the app's own db.

It is also **not re-runnable to correct** — already-annotated rows are skipped, so a mistake needs
manual deletion. Better it runs once, in the right place. **Blocked on `engine/session.py`.**

**A risk worth carrying forward:** `_entry_trading_date` is literally `open_date[:10]` — there is
**no fallback** to a nearby trading day. A position dated to a weekend or holiday becomes unresolved
and halts the whole batch. Halting is the *safe* failure and is deliberate. The hazard is someone
later "fixing" it carelessly. If a fallback is ever added, add it with the reasoning: a Saturday
timestamp can only mean a Friday fill, so the previous trading day genuinely is the correct bar.

## 6. `engine/session.py` — designed, and what it rests on

Full design in `DESIGN_session.md`. The load-bearing decisions:

**Two-phase session.** Phase A calls `decide()`, executes **only** the close intents, and **discards
phase A's open intents** — they were sized against pre-sale cash. Phase B waits for the closes to
reach terminal, **re-reads actual broker cash and equity** (never sums estimated proceeds), rebuilds
inputs, and calls `decide()` again for the authoritative buy side. Bounded to exactly two phases,
never a fixed-point loop.

If an order is still non-terminal at session end, **phase B is skipped**: cash recycling degrades
from same-session to next-session, escalating to a halt after N consecutive such sessions (N is
still open). Rejected: persisting pending orders across nights — that makes the strategy reason
about money in flight, the accumulated state this project avoids.

**All twelve preflight gates are fail-closed.** No fail-open gate anywhere.

**THE BIGGEST UNSIZED RISK: live eToro order latency has never been measured.** The two-phase
session commits to multiple broker round-trips inside a 30-minute window, and `DESIGN.md` itself
calls order latency the standing highest-risk unknown. The design is sound in principle and
completely unsized in practice. Friday is the first chance to find out.

## 7. The SCHG close path (decided 2026-09-06)

The ladder tracks UPRO per-lot but SCHG only as the scalar `schg_position_value`, so **it cannot
supply SCHG lot refs.** The executor must choose lots. Decided:

- **Partial closes ARE used.** (The operator first said no on 09-05, then reversed after considering
  the impact on the strategy as a whole.) `close_position` currently hardcodes `UnitsToDeduct: null`
  — that scope decision **must be revisited**; a partially-closed position stays **open with reduced
  units**, so `lot_annotations` needs an update-in-place path and `reconcile.py` a new invariant.
- **Order by highest cost PER SHARE** — the broker's `openRate`, descending, tie-broken by
  `position_id`. Rejected: highest *total dollar* cost, because every app-created position opens at
  exactly `$50`, so all future lots tie and the ordering degenerates.
- **Order by cost, size by market value.** The partial amount, the shortfall arithmetic and the $10
  check all use current market value. Cost basis is for ordering only.
  **Watch the field:** `Position.amount` is **cost basis**, not market value — `amount == units *
  openRate`, verified 227/227 against the live account. Market value must be computed as
  `units × price` (`mark_position()`'s `PositionMark.current_value`). An earlier draft of this
  design used `Position.amount` for sizing; that would have been wrong on every appreciated lot.
- **UNVERIFIED, and it decides whether a close is legal:** does the broker's $10
  `minPositionExposure` / `minPositionAmount` floor apply to a remainder's **market value** or its
  **cost basis**? The design assumes market value. On an appreciated lot the two differ, so a
  remainder could satisfy one and breach the other. Worth checking on Friday while the market is
  open, or at minimum before the executor is trusted with real money.
- **The $10 stub rule is the binding constraint.** Both `minPositionExposure` and
  `minPositionAmount` are **$10**. Worked example the design must reproduce: need **$51**, positions
  worth **$50/$50/$60** → close the $50 whole, take **$1** from the $60, leaving $59. Taking $51
  from the $60 is illegal — it leaves a $9 stub.
- **Aim to MEET the target**, and since proceeds are never predicted, it is a loop: sell → read
  actual cash → if short, sell the shortfall. **Bounded**: a small deliberate buffer on the first
  pass so the loop rarely fires, a hard iteration cap, and a minimum viable top-up below which it
  stops and accepts the shortfall (phase B simply buys less).

**Scaling risk.** The book is **bimodal**: 202 legacy adopted lots averaging ~$222, plus future app
lots opening at $50. A sell touches ~2–3 lots today and ~10 as the book matures — **order count per
session grows over time**, multiplying the unmeasured per-order latency. ~~Ties directly to the
unset `max_orders_per_session`.~~ **UPDATED 2026-09-06: `max_orders_per_session` is retired —
operator decision, see DESIGN.md §6.C.** An arbitrary order-count cap added no safety once buying
and selling were already dollar-capped (sleeve-cash re-check; core-floor check), so this scaling
risk is now addressed by a latency-derived time gate (`now + measured_p95_latency <
hard_deadline`, `engine/order_budget.py`) that self-adjusts as order count grows, rather than a
fixed integer someone has to notice is stale and re-tune. That gate is explicitly simple
scaffolding, not a settled design — Friday's latency measurement (§8 below) is what gives it a
`p95_latency` to work with.

## 10. Measured on-device (z10, real payloads, 2026-09-05)

Full-history parse + derive: **~0.8–1.2 s, ~4.6 MB peak** — trivial. Scales linearly.

**But the first `exchange_calendars` call in a fresh process costs 13–19 SECONDS**, independent of
payload size, then ~13–22 ms thereafter. Against a 30-minute budget that is ~1% and no schedule
risk — but if vivo's background killer takes the process between nights it recurs **every night**.
**Warm the calendar at wake-service start.**

## 11. Gotchas (additions to the previous handoff's list, which still applies)

- **Never add an unguarded exported Android component.** A `BenchReceiver` with
  `android:exported="true"` and no permission guard was added this session to trigger a benchmark
  past the device's pattern lock. It has been **removed** — an intent extra on the already-launchable
  `MainActivity` does the same job with no new surface. Remaining exported components are only
  `MainActivity`, `BootReceiver` and `ExactAlarmPermissionReceiver`, all pre-existing and required by
  Android. `SessionAlarmReceiver` and `WakeService` are correctly **not** exported.
- The launchable component is `com.nightwatch.etoro.probe.MainActivity` — note the `.probe.`
  segment. `am start -n com.nightwatch.etoro/.MainActivity` fails.
- `get_instruments` does **not** carry `allowPartialClosePosition`; `get_eligibility` does.
- `get_instruments`' ticker field is `symbolFull` (confirmed live, documented nowhere).
- **Tiingo IS reachable from the dev PC** (unlike eToro). Only the eToro side must run on-device.
- The source strategy deducts a flat 5bps commission; **the port deducts nothing**, because the
  measured eToro fee is a size×time carrying charge, not a commission. Do not "restore" the 5bps.
