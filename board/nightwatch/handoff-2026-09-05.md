## 1. Read this first — what actually shipped today

Three things were built, all completed:

1. **`_parse_position` fixed** (`etoro/client.py`, DESIGN_market_data.md §4.2/§10.7). It used to
   read four keys — `currentRate`, `invested`, `unrealizedPL`, `symbol` — that do not exist on a
   live position. It now reads only the fields confirmed to exist (`positionID`, `instrumentID`,
   `units`, `openRate`, `amount`, plus optional `leverage`/`isBuy`/`openDateTime`), resolves symbol
   through `instrumentID` → `instruments` instead of a nonexistent string field, and **raises**
   `EtoroValidationError` on a missing required field instead of silently defaulting.
2. **Gate 10's freshness check built** (`engine/preflight.py`), previously a comment-only stub.
   It validates whichever source supplies the provisional close (Tiingo IEX primary, eToro candles
   fallback — never the rates endpoint), cross-checks eToro's own rates against its own candles for
   every managed symbol including SPY, and — added later the same session — checks the **candle's
   own freshness** via a `Candle.timestamp`/`Candle.interval` pair that did not exist before today.
   Only gate 10 item 1 (freshness) and item 3 (sanity) are implemented; items 2/4/5 and every other
   gate remain stubs (§7 below).
3. **The §4.7 adoption migration built** (`market/adopt.py`, `db/migrations/003_lot_annotations.sql`,
   plus `Repo.insert_lot_annotations`/`insert_lot_annotation`). Backfills `lot_annotations` for the
   209 pre-existing SCHG/UPRO positions gate 11 invariant 1 would otherwise halt on forever. Has a
   dry-run mode (`build_adoption_plan` without the write), is idempotent (`INSERT OR IGNORE` keyed
   on `position_id`), and atomic (one transaction, all-or-nothing per the task brief's explicit
   requirement that a partial backfill is worse than none).

Two more parser bugs of the **same defect class** were found and fixed along the way, not planned
at session start:

- **`get_balance`** used to call `/balances` and read `credit`/`orders`/`ordersForOpen` off it.
  None of those fields exist on that endpoint — its body is just `{"totalBalance": ...,
  "balances": [...]}`. The old code silently computed `available_cash = 0.0` with no error. Since
  `broker_available_cash` feeds `sleeve_cash` (DESIGN.md §4.5), this would have zeroed the entire
  cash sleeve with no diagnostic pointing at the cause — fails closed (the app just never buys),
  but silently. Fixed: `get_balance` now reads `credit`/`orders`/`ordersForOpen` off the
  **portfolio** endpoint's `clientPortfolio` envelope (the same one `get_portfolio` already
  unwraps), and raises if `credit` is absent rather than defaulting to `0.0`.
- **`_parse_trade_history_entry`** used to read `positionID`, `symbol`, `action`, `profit`,
  `openDateTime`, `closeDateTime` — none of which exist on a trade-history row. Fixed the same way:
  real keys, raise on a missing required field. See §5 below for the financial-arithmetic findings
  this fix surfaced.

**All three are the same bug, found three times in two days**: a parser reads a key name that
looks plausible and isn't there; the library defaults it to `None`/`0` instead of raising; nothing
in a demo-account test ever exercises the code path because the demo account holds zero positions
and zero trade history. `_parse_position` was found on 2026-09-04, `get_balance` and
`_parse_trade_history_entry` both on 2026-09-05.

## 4. The parser-bug pattern — read before writing another eToro client method

Every bug found this session and last has the identical shape: a field name that is plausible,
absent from the live payload, and silently defaulted rather than erroring. It was invisible for
months because the only account ever tested against was a demo account with **zero** positions and
(implicitly) untested trade history — a check that passes because nothing happened is not a pass
(carried forward verbatim from HANDOFF_2026-09-04 §8's own framing of `_parse_position`).

**A fourth instance, one layer down — not a wrong key name but a wrong assumption about a
*value*.** Both `_parse_position` and `_parse_trade_history_entry` resolved their id via an
`or`-chain: `raw.get("positionId") or raw.get("positionID") or raw.get("id")`. A legitimate id of
`0` is falsy, so the chain does not merely lose it — **it falls through and returns a different
key's value**, silently mislabelling the position as another one. Fixed 2026-09-05 by explicit
`is not None` lookups, with a regression test that asserts `0` *wins over* a wrong value in a
fallback key (asserting "it does not crash" would not have caught this). Latent in practice —
eToro ids are large integers — but it is the same family: a plausible-looking default quietly
standing in for a fact. **When auditing the parsers in §8, check truthiness assumptions as well as
key names.**

**The fix pattern, now applied four times and worth reusing verbatim for anything still
unverified (§8's list):** parse only fields confirmed to exist against a real payload; raise
`EtoroValidationError` on a missing required field; never default a financial field to `0.0` or
`None` and let execution continue. `get_balance`'s docstring states the principle plainly: *"a
silent zero is worse than a crash."*

**A fifth instance, found the same day this document was updated — not a wrong field name, and
not a wrong truthiness assumption, but a wrong assumption about the response *envelope*.**
`get_trade_history` assumed the trade-history body was `{"items": [...]}"`. The live body is a
**bare JSON list** (§10.17 of DESIGN_market_data.md). The old code's own attempted fallback —
`data.get("items", data if isinstance(data, list) else [])` — looked like it handled exactly this,
but could not: `data.get` is evaluated before its `isinstance` fallback is ever considered, so a
bare list raised `AttributeError: 'list' object has no attribute 'get'` and the fallback never
ran. Fixed by branching explicitly on `isinstance(data, list)`/`isinstance(data, dict)` and
raising on neither. **The pattern is now five instances of the same defect class, not four** —
the first four were all "a field name that looks plausible and isn't there"; this one is the same
family one layer up, "an envelope shape that looks plausible and isn't there." **The meta-lesson
this instance adds:** every pre-existing test for this method wrapped its fixture rows in
`{"items": [...]}"`, so the test suite encoded the same wrong envelope assumption the production
code made, rather than checking it — a fixture that agrees with a bug is not a check on the bug.
See DESIGN_market_data.md §10.18 for the full writeup.

**The casing trap, confirmed across two endpoints today:** the portfolio endpoint uses
`positionID`/`instrumentID` (capital `D`); trade history uses `positionId`/`instrumentId`
(lowercase `d`). eToro is inconsistent **across its own endpoints**, not merely wrong in one place.
Any new client method must probe its own payload rather than assume either casing convention
transfers.

## 5. Financial findings — record these precisely, they are easy to get wrong

Measured across all **120** real closed trades in the account's full history (§10.5, no retention
cutoff found):

- **`netProfit` is not net of `fees`.** Σ`netProfit` = **+$327.25**; Σ`fees` = **−$380.40**. Reading
  `netProfit` alone on this book of trades reports a **profit**; the all-in result, after fees, is
  a **$53.15 loss**. Any P&L surface (dashboard, Telegram summary, `budget_history`) that reports
  `netProfit` without subtracting `fees` will be wrong in the flattering direction.
- **The verified closed-trade P&L formula is `investment × (closeRate / openRate − 1) − fees`** —
  matches `netProfit` within $0.02 on **120/120** rows, max error $0.0091.
- **The units-based formula, `units × (closeRate − openRate)`, is markedly worse** — matches only
  **117/120** within $0.02, max error $398.51, and is worse still once `fees` is added to it (mean
  absolute error 3.20 vs. 0.0032 for the investment-based formula).
- **The asymmetry that matters:** `amount ≈ units × openRate` holds **227/227** on **open**
  positions, but its closed-trade analogue (`investment ≈ units × openRate`) holds only **116/120**
  on **closed** trades — 4 rows disagree, one by 72×. **Do not carry the open-position invariant
  over to closed trades.** The trustworthy quantity on both endpoints is the **money field**
  (`amount` open, `investment` closed) — `units`/`openRate` are not reliable on either.

All of the above is measured across every row in the dataset, not a sample — stated here because
an earlier draft of one of these findings called the one mismatching row "a data anomaly" before a
full 120-row check found three more like it.

## 9. Gotchas — carried forward and new this session

- **The eToro DNS sinkhole is unchanged.** The dev PC still cannot reach `public-api.etoro.com` or
  `www.etoro.com` at all (Kominfo sinkhole, same as HANDOFF_2026-09-04 §8). All eToro-touching work
  — probes, tests against a real payload, anything — must run on-device.
- **`INSERT OR IGNORE` silently swallows a SQLite `CHECK` violation** while still **raising** on a
  `FOREIGN KEY` violation — independently verified against this project's SQLite build (3.49.1).
  This is exactly the "didn't error, not a pass" trap this project keeps hitting, one layer lower:
  `Repo.insert_lot_annotations` needs `INSERT OR IGNORE` for idempotency (§1 above), but that same
  clause would silently skip a row with an invalid `book`/`origin` instead of raising — so
  `Repo._validate_lot_annotation` duplicates both `CHECK` clauses in Python and runs **before** any
  `INSERT` is issued, specifically to catch what SQLite would otherwise swallow. Do not assume
  `INSERT OR IGNORE` and a `CHECK` constraint together give you a loud failure — they don't.
- **eToro's field-name casing is inconsistent across its own endpoints, not just internally
  wrong.** `positionID`/`instrumentID` (capital `D`) on the portfolio endpoint; `positionId`/
  `instrumentId` (lowercase `d`) on trade history. A parser that assumes one casing convention
  transfers to a new endpoint will silently succeed on the wrong field via `.get()`'s fallback
  chains — as `_parse_trade_history_entry`'s old `instrument_id` field did, by accident, before
  today's fix.
- **`MaxDate` is silently ignored server-side on trade history.** A `MinDate=2024-08-01,
  MaxDate=2025-01-01` query still returns trades closed through the account's actual latest close.
  Any upper bound on trade history must be enforced **locally**, never assumed server-applied.
  Confirmed live 2026-09-05; the client's own local `_closed_on_or_before` filter was itself
  silently inert until the same day's field-name fix (it was comparing a field that was always
  `None`), so an earlier fix depended on a later one to actually work — check the whole chain
  when fixing one link.
- **The saved probe payloads are now the antidote to assumed field shapes.** Every parser fix this
  session and last came from reading a real payload, not from re-reading eToro's own documentation.
  Treat any field name in DESIGN.md or DESIGN_market_data.md that has not been checked against a
  saved live payload as a hypothesis, not a fact, until it has been.
