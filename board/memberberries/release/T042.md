## Outcome
Every host, MCP server and hook shares one resident embedding model, so there is one model in memory and no per-prompt load. This is the Phase 2 intent of a managed model service, done without a listening network port.


## Scope
crates/memb-rag client, a new service mode of memb, memb-win named pipe helpers, wiki.


## Plan (Todo Tree)
- [ ] A1 [START] [lane:main] Design and record: the long-running memb process (daemon or a dedicated service) holds the one embedding model and answers embed requests over a per-user Windows named pipe (no TCP port, access limited to the current user), started on demand and unloaded when idle; every MCP server instance and every hook uses it; record the departure from the approved stdio-only decision and get the user's approval
- [ ] A2 [lane:main] [after:A1] Client in memb-rag: embed through the service, start it if absent, fall back to lexical search (never to loading the model in the caller) if it is unavailable or slow
- [ ] A3 [lane:main] [after:A2] Service: single model instance, request queue with a bound, idle unload, memory governor, version and model identity handshake so clients never mix vectors
- [ ] T1 [lane:test] [after:A3] [ACCEPTANCE:MANDATORY] Measured with the real model: three MCP servers plus hooks share one process (private memory of the client processes stays small, total near one model), a hook with retrieval finishes in well under the hook timeout (today with the model loaded in the hook: 3.3 to 6.3 s on this machine against 0.4 s lexical), a killed service restarts on the next request; cargo test --workspace --locked --offline

## Prove
Real-model run with several clients: memory, hook latency, restart; cargo test --workspace --locked --offline.
